# Code map

Use this page to find an implementation or decide where a change belongs. Read
[architecture.md](architecture.md) for ownership rules, concurrency invariants and
compatibility constraints. Paths below are relative to this document and clickable.
Module roots (`mod.rs`) define their public API; implementation helpers generally
remain private to their domain. Besides the app (`src/`) and the domain crates
described in [architecture.md](architecture.md) (model, interop, catalog, engine,
decode and export, under `crates/`), the workspace has
[`crates/rawmakase-protocol`](../crates/rawmakase-protocol/src/lib.rs)
(what the app and its control clients agree on: protocol version, `control.json`
endpoint, data folder) and [`tools/rawmakase-ctl`](../tools/rawmakase-ctl/src/lib.rs)
(the control client, used by `rawmakase control`, `rawmakase mcp` and the
standalone `rawmakase-ctl`). The last two build without the app.

| [crates/rawmakase-decode/src/dev/half_check.rs](../crates/rawmakase-decode/src/dev/half_check.rs) | A RAW file's half-size check (`rawmakase half-check`): its half-size decode against its full decode reduced (block CIEDE2000, Laplacian detail) and its half ÷ full time, with the gates against the file's recorded reference. `scripts/corpus/dataset-half.py` runs it on the test dataset. |
| [crates/rawmakase-decode/src/color_difference.rs](../crates/rawmakase-decode/src/color_difference.rs) | CIELAB of linear sRGB and CIEDE2000, which Camera Look's fit and the half-size checks measure with. |
| [crates/rawmakase-decode/src/camera_look/](../crates/rawmakase-decode/src/camera_look/mod.rs) | Camera Look (fitted), `rawmakase fit-look` ([Lightroom profiles](lightroom-profiles.md#camera-look-fitted)): `pairs` picks and converts the embedded JPEG, aligns it with the photo's small render and masks what can't be learned; `solve` fits the look's curve and table and, for a camera without a matrix, a forward matrix from the camera input stage; `gate` scores full renders on held-out tiles and accepts or refuses. `with_default` is the default fit of a photo without colour data, through the fit cache (`cache`); fitting is deterministic and reads no catalog. |
| [crates/rawmakase-decode/src/raster.rs](../crates/rawmakase-decode/src/raster.rs) | Opens a JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL (by content, whatever the extension): for an unedited one in the Library, decoded upright and converted from the embedded ICC profile (16-bit samples at 16 bits) to 8-bit sRGB through `moxcms`, for the Library's thumbnails, screen previews and Loupe. A file without a usable RGB or grey profile is taken as sRGB. `open` is the Develop decode, crate-private and reached only through `photo::open_source`, which converts its result to the pseudo-scene: the same setup, converted to linear ProPhoto D50 f32 into a `CameraImage` marked `Source::Rendered` (identity white balance and matrix, EXIF camera and exposure when present, alpha dropped); CMYK and other colour spaces, HDR that doesn't decode exactly (HDR HEIC, gain maps, other primaries; see [HDR](hdr.md#hdr-files) for what opens as HDR), animated files (APNG among them), narrow-range PNG cICP, tiled AVIF and HEIF without a system decoder are refused with `Unsupported`, which `probe` finds from the header and profile alone; HDR and animated files still give the Library a plain preview (an HDR one tone mapped to SDR from its 203-nit reference white, linear light above 1 kept until then, and HLG's system gamma applied on luminance). A TIFF's ICC profile is read apart from `image` when it drops a small image's (`tiff_icc`), a tiled AVIF none. `dimensions` reads a file's size through the same decoder, for `catalog_session/backfill.rs`. Its EXIF comes from `rawmakase-interop`, which the decode crate depends on directly. |
| [crates/rawmakase-decode/src/raster/jxl.rs](../crates/rawmakase-decode/src/raster/jxl.rs) | A JPEG XL file through jxl-oxide's `image` decoder, which renders it upright by its codestream, so no EXIF rotation is applied after it. |
| [crates/rawmakase-decode/src/raster/av1.rs](../crates/rawmakase-decode/src/raster/av1.rs) | The safe side of rav1d (dav1d in Rust, built without assembly): one AV1 still decoded to its planes; a cut-off stream is an error, not a wait. |
| [crates/rawmakase-decode/src/raster/avif.rs](../crates/rawmakase-decode/src/raster/avif.rs) | An AVIF still: its container read by `isobmff`, its AV1 decoded by `av1` and turned into RGB with the matrix and range the file says (`yuv`); colour from the `colr` boxes (ICC, or CICP), sRGB when it has none; 10- and 12-bit 4:2:0 chroma is upsampled here (`deep420_to_rgb`), as `yuv`'s ARM code for it is wrong. What it shares with `heic` is in `heif.rs`. |
| [crates/rawmakase-decode/src/raster/heif.rs](../crates/rawmakase-decode/src/raster/heif.rs) | What AVIF and HEIC files share as HEIF images: an item's colour (ICC, or a profile built from its CICP code points), its orientation from `irot` and `imir`, and widening decoded samples. |
| [crates/rawmakase-decode/src/raster/heic.rs](../crates/rawmakase-decode/src/raster/heic.rs) | A HEIC still from its header, read by `isobmff`: a single picture or a grid's tiles, its size and `clap` crop, colour (the image's or its first tile's `colr`), orientation, and refusals for Develop (HDR, sequences); header reading is bounded (associations no more than items, each tile and each `hvcC` read once, an `hvcC` of at most 16 KiB) and the tiles, with an alpha image's, are held to 150 MP. Its pixels come from `heic/imageio` on macOS, `heic/wic` on Windows and `heic/libheif` elsewhere; `heif_decoder` says whether the system can decode them, or what to install; before any decoder reads them, every picture's data, the alpha's too, must be in the file, together (each stored location once) no larger than it, and the pictures at the size their SPS code them (in a tile's `hvcC` or among its NAL units, padding and all) may take no more than 150 MP together; they are cropped here, unless the decoder cropped them, and any other size is refused before it is allocated. |
| [crates/rawmakase-decode/src/raster/heic/imageio.rs](../crates/rawmakase-decode/src/raster/heic/imageio.rs) | A HEIC's pixels on macOS: the primary image decoded by ImageIO, from the bytes of the file the header was read from, and drawn by CoreGraphics into a bitmap of the colour space and depth the header says (CoreGraphics' own PQ or HLG space for an HDR CICP; sRGB for a profile moxcms or CoreGraphics can't read as RGB), in an autorelease pool, decoded when it is made and refused if it doesn't draw (ImageIO decodes lazily, and a failed decode drew a black photo), unless, transparent everywhere, its decoded pixels are there; alpha comes out composited over black; not turned, and cropped by `heic.rs` unless ImageIO cropped it. |
| [crates/rawmakase-decode/src/raster/heic/wic.rs](../crates/rawmakase-decode/src/raster/heic/wic.rs) | A HEIC's pixels on Windows: decoded by Windows Imaging Component (Microsoft's HEIF Image and HEVC Video Extensions) through the handle of the file the header was read from and converted to RGB of the header's depth; when it fails, the error gives WIC's reason and says what to install if no HEIC photo opens. Not turned; cropped by `heic.rs` unless WIC cropped it. |
| [crates/rawmakase-decode/src/raster/heic/libheif.rs](../crates/rawmakase-decode/src/raster/heic/libheif.rs) | A HEIC's pixels on Linux and other systems: the system's libheif, opened with `dlopen` when first needed and kept open, decodes the bytes read through the header's open file, uncropped and unturned, to RGB of the header's depth (alpha dropped); without libheif or its HEVC decoder, the error says what to install. ### Background work

What each long-lived worker blocks on, how it stops and whether exit may wait for it: [the shutdown contract](shutdown.md).

| File | Responsibility |
| --- | --- |
| [worker/mod.rs](../src/app/worker/mod.rs) | Named event payloads, load/render jobs, task kinds, render stages and repaint notification. |
| [worker/latest.rs](../src/app/worker/latest.rs) | Single-slot mailbox: submitting a new job replaces pending work rather than growing a queue; optional lanes each keep their own latest job. A panicking job does not end the thread. |
| [worker/loader.rs](../src/app/worker/loader.rs) | Opening a photo for Develop: metadata and profiles, then for a RAW its embedded preview, the half-size then full decoded image and the neighbour's prefetch; a rendered file (JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL) goes straight to its full-size image, never through the decode cache, and its prefetch is held in memory for the next load. ## How an operation moves through the app

1. **Open a photo:** workspace/dialog/catalog actions enter `app::develop::workflow`. It
   flushes the old document, resets document state, starts a load generation and
   submits a loader job. The loader uses `raw`, `camera_profiles` and `storage`.
   `app::events` accepts only current results. A saved catalog recipe, when present,
   replaces the loader's resolved defaults for a catalog photo.
2. **Edit and preview:** panels change the recipe. `app::develop::editing` and `history`
   group the change; save policy marks it pending. `workflow` submits the effective
   recipe and viewport to the renderer. The worker calls `develop`; with a usable
   GPU and a recipe the GPU stage covers (every recipe resolved with a camera profile, see
   `pipeline/pixel_params.rs`), the color and tone stage and the finishing run on
   the device and the result is drawn straight from its texture; otherwise the
   worker renders on the CPU and prepares the display bytes. Accepted results
   become the preview. At 100%, an edit or pan whose region is not already cached
   and takes more than a moment publishes a reduced draft first, then the
   full-resolution region.
3. **Save edits:** workspace autosave and navigation/close flushing call
   `workflow`; autosave writes in the background (`autosave`), and flushing
   waits for it before saving synchronously. Photos are edited only through the
   Library, so edits always save through `catalog`. An edit the catalog cannot load
   is protected and cannot autosave, and failed writes remain pending for retry. Presets are separately saved reusable recipes.
4. **Export:** foreground activity coordinates destination/overwrite handling.
   The export job captures the recipe, renders through the development API, then
   calls `export` to encode and publish, in the colour space the export settings
   chose (sRGB by default) and with its profile, independently of the monitor
   profile. Navigation is held during export.
5. **Apply a preset:** `presets` discovers assets, `xmp` parses/translates Adobe
   settings, and the app handles compatibility and hover state. Hover is temporary;
   application commits a recipe through the editing/history flow.
6. **Import Lightroom:** the app or CLI calls `catalog::lightroom`. It reads a
   source snapshot, preserves source data, transfers relationships, and publishes
   a new native catalog. Develop translation is best effort and reports unsupported
   settings; it does not promise Lightroom rendering parity.

## Where data lives

`storage::data_dir()` selects `RAWMAKASE_DATA_DIR` when set. Otherwise it uses
`~/Library/Application Support/RAWmakase` on macOS and `$XDG_DATA_HOME/rawmakase`
(default `~/.local/share/rawmakase`) on Linux.

| Data | Location and lifetime |
| --- | --- |
| Original RAW and Lightroom catalog | User-selected source files; treated as read-only. |
| Legacy sidecar edits | Adjacent `photo.ARW.rawmakase.json` / `photo.RAF.rawmakase.json`, plus `photo.ARW.rawmakase-local.json` for spots and masks, or identity-keyed JSON under the data directory's `sidecars/`, saved by releases before 0.1.8. Imported into the catalog when their folder is added and left on disk unchanged. |
| Native catalog | User-selected `.rawmakase` SQLite file; authoritative catalog metadata, edits and preserved import data. Spots, red eye corrections and masks are in the `local_edits` table, Develop History in `develop_history`, raster data in `bitmaps`. |
| Native preset / exported photo | User-selected JSON / JPEG / TIFF / PNG destination. |
| Session preferences | `session.json` in the data directory ([session.rs](../src/app/preferences/session.rs)); the last catalog and place, panels, layouts and preferences. Each field reads leniently (a malformed one resets alone), fields a later release wrote are written back as read, and the output stays readable by older releases (`copy_groups` never names AI Denoise, which v0.4.10 cannot read). UI tests inject a temporary destination or disable writes. |
| Preset favorites | `preset-favorites.json` in the data directory. |
| Imported preset backups | `preset-backups/` in the data directory: an imported preset as it was before its first Update with Current Settings, at its path under `xmp-presets/Imported/`. |
| Saved point curves | `curves/` in the data directory: one XMP file per curve, named by the curve. |
| Installed assets | `xmp-presets/` and `camera-profiles/` under asset roots; shared discovery also checks the legacy XDG/Linux data location. Imported XMP files go to `xmp-presets/Imported/` under the current data directory. |
| Library previews | `previews.sqlite3` in the data directory; disposable cache, not a source of edits. |
| Decoded photos | `decoded/` in the cache directory (`~/Library/Caches/RAWmakase` on macOS, `$XDG_CACHE_HOME/rawmakase`, default `~/.cache/rawmakase`, on Linux; `%LOCALAPPDATA%\RAWmakase\Cache` on Windows; `RAWMAKASE_CACHE_DIR` overrides it), or `RAWmakase Cache/` in the folder chosen in Preferences > Performance: developed camera images of opened and prefetched photos, capped at 4 GiB by default (Preferences > Catalog > Decoded images changes the limit), least recently used removed first. Disposable. |
| AI Denoise results | `ai-denoise/` in the cache directory, or `RAWmakase AI Denoise/` in the folder chosen in Preferences > Performance, which moves and purges them with decoded photos: one `.aidenoise` file per job key (file identity, model SHA-256, adapter version, provider, build), capped at 10 GB, least recently used removed first. Disposable; saved edits never need it. The model itself installs in `models/rawnind-utnet2-bayer-v1/` in the local data directory, with its `LICENSE`, `NOTICE` and model card. |
| Build output | `target/`; generated binaries, documentation and local macOS bundle. |

### Camera parity diagnostics

`scripts/cameras/check-calibration.py` audits converter metadata against the camera
table; `data/camera-calibration-facts.json` holds public-sample and anonymous local numerical evidence.
`scripts/cameras/parity.py` captures and verifies Camera Raw renders and compares
frozen references with RAWmakase. See [camera parity](camera-parity.md).
