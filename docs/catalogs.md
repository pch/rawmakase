# RAWmakase catalogs and Lightroom import

Dropping a folder onto the window adds it and selects that folder (including its
subfolders) in the Library. Dropping several folders selects their combined scope;
unrelated catalog photos stay out of the view. The filter bar clears for the
imported folders so existing filters do not hide the newly added photos.

A folder chosen in the Folders panel shows the photos in it and in its
subfolders, and its count says how many. **Show Photos in Subfolders** in a
folder's right-click menu turns that off, as in Lightroom's Library menu: each
folder then shows and counts only the photos directly in it (a folder holding
only folders shows none), until it is turned on again. The choice is kept with
the Library's layout across launches. Remove from Catalog, Synchronize Folder
and the drives' counts still cover a folder's subfolders.

**Filter Folders**, at the top of the Folders panel, finds a folder among many
without scrolling: type part of its name (in any case) and the panel shows only
the folders whose names hold that text, with the folders above them unfolded,
including those inside folded folders and drives. Unlike Lightroom, the text is
matched as one phrase, not as words any of which may match. The folders chosen
stay shown, as in Lightroom, and typing never changes which photos the grid
shows. **Enter** chooses the first folder found and keeps the keyboard in the
field to refine the text; the folders above it stay unfolded once the field is
cleared. **Escape** leaves the field and keeps its text; the × clears it.

Use **Catalog → Import Lightroom catalog…**, select a closed `.lrcat`, then choose a new `.rawmakase` filename. Existing destination files are never overwritten. **New catalog** creates an empty library; **Add photo folder** recursively registers RAW files (any extension in `RAW_EXTENSIONS`), JPEG, PNG, TIFF, WebP, AVIF, HEIF (`.heic`, `.heif`, `.hif`) and JPEG XL files without copying or modifying them. The last four are read only: they are catalogued, shown and edited, but export to them is not available yet.

**Library** (`G`) provides a virtualized thumbnail grid, folder browsing, filename/keyword/date/label search, minimum-rating and flag filters, offline filtering, capture-date sorting, and rating/flag/color-label editing. Double-click an available photo, a RAW file (see `RAW_EXTENSIONS` in `crates/rawmakase-model/src/storage/files.rs`) or a JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL, or select it and use **Develop** (`D`); an offline photo is refused unless it has an up-to-date editable preview ([editable previews](editable-previews.md)), which it opens from, labelled Editable Preview, with AI masks, AI Denoise and Fit Camera Look off and its edits saved as the original's, as is a rendered file whose header says Develop can't edit its pixels (a CMYK JPEG, an HDR or animated WebP, AVIF, HEIF or JPEG XL, or a tiled AVIF, say; "RAWmakase can't edit HDR images"), with the reason in a dialog and under Quick Develop. A JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL is edited from its own pixels with the Embedded profile and relative white balance, as Lightroom does ([rendered files](color-pipeline.md#rendered-files-jpeg-png-tiff-webp-avif-heif-jpeg-xl)). Until it has an edit, the Library and Loupe show it as its file, converted from its embedded ICC profile to sRGB (a file without one is taken as sRGB), which its defaults reproduce; once edited, it is shown developed, as a RAW is. An HDR or animated file still shows in the Library, as a plain preview of its first frame (an HDR one tone mapped for an SDR screen); a tiled AVIF and a 4:2:2 or monochrome HEIF show nothing. Library thumbnails are original embedded/file previews, not Lightroom-rendered previews.

**Develop** retains the preset browser and editing controls. When the photo belongs to a catalog, edits and export options save in that catalog rather than beside the photograph. Virtual copies share the source photograph but have independent recipes. Create Virtual Copy (⌘' or the thumbnail menu, in Library and Develop) starts a copy from the photo's current edit, rating, flag, label and keywords, named Copy 1, Copy 2 and so on. The thumbnail menu also offers Set Copy as Master and Remove Virtual Copy (which asks first and leaves the file alone); rename a copy in the Library Metadata panel's Copy Name field. Copies show a folded corner on their thumbnail and their own edited preview. Opening a RAW file directly goes through the Library: a photo already in the open catalog develops from it, and an unregistered photo has its folder added to the catalog first, so its edits save in the catalog too. Edits saved beside the file by releases before 0.1.8 are imported when that folder is added, and the sidecar is left on disk. Opening a catalog photo does not implicitly import a possibly unrelated RAWmakase sidecar.

**Stacks** group photos of one folder under one of them, the top, as Lightroom's folder stacks do. Select photos and press ⌘G (or Stacking › Group into Stack in the thumbnail menu): the active photo becomes the top and the stack is collapsed, showing the top alone with a badge counting its photos. Click the badge or press S to expand or collapse it; expanded, its photos sit together in stack order, each marked "2 of 3" and so on, wherever the top sorts. Shift+S makes the active photo the top; the menu also moves a photo up or down, takes photos out of their stack (Remove from Stack) and collapses or expands every stack. ⌘⇧G unstacks. A collapsed stack's top stands for the whole stack to Group into Stack and Unstack; ratings, flags, labels, keywords, Quick Develop, Sync and export apply to the photos selected, so to the top alone, as in Lightroom. A filter shows every photo it matches: when it hides a collapsed stack's top, the stack's first photo that matches shows in its place. All Photographs and folders show stacks; collections and Previous Import list their photos one by one. **Auto-Stack by Capture Time…** (the thumbnail menu's Stacking, or Photo › Stacking in the macOS menu bar, as in Lightroom) stacks photos of each folder shown that are in no stack yet, joining each photo to the one before when it was taken less than Time Between Stacks later (up to an hour; none at 0:00:00), and shows how many stacks it would make before it does. With **Group camera bursts** ticked, it reads what each camera wrote in its maker note: a burst or bracket becomes one stack, first frame on top, however long it took, and two bursts shot within Time Between Stacks of each other stay apart. Sony (SequenceNumber, 0xb04a), Fujifilm (0x1101) and Panasonic (0x002b, read from an RW2's JpgFromRaw) number each press's frames from 1, so a run of rising frame numbers from one body and in one format is one burst, each frame at most a minute after the one before; culled frames leave a burst whole, but a burst whose first frames were deleted joins the one before it if shot within that minute. Two bodies of one model tell apart only by the EXIF's body serial number. Photos taken in the same second follow their file names. An iPhone gives a burst's photos one BurstUUID. Olympus and OM System bodies number some sequences' frames too (DriveMode's shot number). Canon (ContinuousDrive and BracketMode; its own counter is 0 in most files) and Nikon (ShootingMode) say only whether a photo was shot in continuous drive or a bracket: those photos stack by capture time as Auto-Stack does, each body's and format's apart, so two presses less than Time Between Stacks apart make one stack, and a single shot or a numbered frame of the same body ends the run. A DNG Adobe converted is read from the camera's note it keeps (DNGPrivateData's MakN block, even when Camera Raw copied it from 12 bytes too early; for a Panasonic, the JpgFromRaw in its Pano block), a CR3 from its CMT3 box. A photo the camera says was a single shot is left alone; photos of other cameras (older Sony bodies such as DSLR-A, NEX and SLT, Pentax, Leica…) and unreadable files stack by time, never across a photo whose camera said something. Virtual copies are left alone. What the maker notes say is kept in the catalog (`photo_sequences`) with each file's size and modification time, so a file is read once and again only when it changes: a photo added from a folder has it read in the background with its photo info. When the box is first ticked, the window checks each candidate's file (one stat), takes what the catalog kept of a file that is unchanged, and reads and saves the rest (photos imported from Lightroom, those added before this release, files replaced since); an offline file stacks by time and nothing is saved of it. Stack waits for them, and stays off if the read stops before every photo (untick and tick the box to read again). A release that reads more cameras' notes reads every file again once. Releases before it ignore the table. **Stack camera bursts** in Preferences › Catalog › Adding photos (off by default) does the same for photos added from folders and by Synchronize Folder, without being asked: once their files are read in the background, each burst or bracket becomes a collapsed stack as Group camera bursts makes it, frames a camera didn't number (Canon's, Nikon's continuous drive) joining while less than two seconds apart; photos whose camera says nothing, or that are in a stack by then, are left alone, and nothing is stacked by time. The choice is taken when adding starts and kept with the batch in the catalog (`import_burst_stacks`) in the transaction that adds its photos, so the stacking survives a restart or another catalog being opened meanwhile; it is done in the Library, with nothing open over it (it waits while Auto-Stack's window is open, a file operation or Synchronize holds the catalog, or the window shows Develop), as one step for Undo, after which the batch is done and Undo leaves it unstacked. A batch with a photo offline waits until it is back; one whose read stopped is read again when the catalog opens or its files' availability changes. Export as Catalog leaves the batches still to be stacked behind, and a release before this one refuses to export a catalog with the new table, as it does any table it doesn't know. Each change, Auto-Stack's included, is one step for Undo; collapsing and expanding are kept with the catalog and aren't. A new virtual copy goes right after its photo in its stack (or makes a stack of the two), expanded so it shows. A photo moved to another folder leaves its stack; renaming photos or a folder, or moving a whole folder, keeps them. Removing a photo takes it out, and a stack left with one photo is no stack. Stacks are kept in the catalog only, never in XMP; importing a Lightroom catalog brings its folder stacks, with their tops and whether they are collapsed. Lightroom's collection stacks aren't imported. Releases before stacks open a catalog with stacks and leave them be; what they remove or move is read correctly afterwards.

**Delete** or Backspace in the grid, the Loupe or the filmstrip (in Develop, while no tool is open) asks, as Lightroom does, whether to **Move to Trash** or just **Remove from Catalog**; photos whose files are missing or offline are only offered Remove from Catalog. **Remove from Catalog** takes photos out of the catalog and leaves their files where they are: press ⌥Delete, or choose Remove from Catalog… in the thumbnail menu, to ask for it alone. It acts on the selection, or in the Loupe on the photo shown; the Loupe then stays open on the next photo, or the one before when the last went. A master takes its virtual copies with it; copies chosen without their master go alone. RAWmakase asks first, and says how many photos and copies go and how many have edits made in RAWmakase. Those edits, with the photos' ratings, keywords and History, go with them: adding the file again doesn't bring them back. In that question Cancel has the focus, so Return, Space or Escape alone cancel; Remove from Catalog needs a click, or Tab to it first. A key still held when the question appeared (Delete repeating) does nothing until it is released. The open edit is saved before anything is asked, and if it can't be saved nothing is removed. While photos are being removed the top bar says so, with Stop, which ends it after the photo under way. Delete in the Quick Collection, or any other collection (one imported from Lightroom too), only takes the selected photos out of it, as one step Undo brings back; in a collection set it does nothing and the status line says so.

**Move to Trash** puts photos' files in the system Trash (the Recycle Bin on Windows, the freedesktop Trash on Linux), with the XMP sidecars and earlier releases' edit files only they read, then takes the photos, their virtual copies included, out of the catalog. Choose it in Delete's question, press ⌘⌥⇧Delete, or choose Move to Trash… in the thumbnail menu. The question says how many files and sidecars go, and that edits made in RAWmakase go with the photos: putting a file back from the Trash brings back the file, not its edits. Move to Trash never deletes anything outright: a file goes to the Trash or stays, and the catalog lets a photo go only once the Trash has its file and it is gone from its folder. A photo whose file has another name on its drive (a hard link) goes as well, as in Lightroom: only its own name goes to the Trash, and the file stays under its other names, so no space is freed. It stays when another photo of the catalog is that file under one of its other names, and the top bar names that photo. Such a photo isn't moved or renamed. Photos on a drive with no Trash (an SMB share such as a NAS, or a drive the system's Trash says can't take them, as Windows' says of USB sticks and network drives) are left out of Move to Trash when it is asked, and the question says so; one whose drive turns out to have no Trash only when it runs keeps its file and photo, and the top bar says to delete it in Finder if you're sure. **Delete Permanently…** (#1273), offered in Delete's and Move to Trash's question when any of the photos are on a drive with no Trash, deletes their files outright, as Lightroom does when asked about files on a volume without a Trash. It always asks again on its own first: the question warns in red that this can't be undone, that the files don't go to the Trash and nothing can bring them back, and counts the files and sidecars deleted; Cancel has the focus, and Remove from Catalog, which keeps the files, stays the first question's main action. When Move to Trash can take none of the photos, ⌘⌥⇧Delete asks Delete Permanently's question straight away. Photos on a drive with a Trash, or one that can't be told, are never deleted permanently. Each file is deleted only while it is still the file asked about (its file object, size, date and first bytes), with the sidecars only it reads, journalled as it goes, and the photos (their virtual copies included) leave the catalog once every file of theirs is gone. One changed since the question leaves the photo as it is; one that can't be deleted after its photo's file was leaves it under **Unfinished file operations**, never put back, to **Remove from Catalog** once the photo's own file is gone (the files left stay) or **Keep as Is**. **Delete Rejected Photos…** (⌘Delete, or the Catalog menu) asks the same as Delete for the rejected photos of the folders or collection shown, whatever is selected or filtered.

**Moving photos to another folder** moves their files on disk, and the catalog follows. Drag the selected photos from the grid onto a folder in the Folders panel, or choose **Move to Folder…** in the thumbnail menu and pick a catalog folder. **New Folder Inside…** in a folder's menu makes a folder there, on disk and in the catalog, and offers to move the selected photos into it (ticked when they are all in that folder). A master's virtual copies go with it, and so do the XMP sidecars and earlier releases' edit files only it reads; one another file reads too stays where it is. RAWmakase asks first, saying how many files and sidecars move and which photos stay and why, with Cancel focused as for Remove from Catalog; a folder made with nothing moving into it is made on Create. The destination may also be a folder of a root that has no photos of its own yet (one holding only folders, or a root folder with photos only below it): its directory must be there, and its folder joins the catalog in the same step the photos' rows follow, never before. Within a drive files move by renaming them, so their bytes and dates don't change and their edits and checksums stay valid; nothing is ever replaced: a name taken in the destination (on disk, or by a photo of the catalog, even an offline one) leaves that photo where it is. To another drive (an external disk) each file is copied instead: into a hidden `.<name>.<run>-<item>-<file>.rawmakase-part` file there (which Synchronize Folder and Add Photo Folder pass by), read back and compared with what was read of the original (SHA-256), given the original's extras (its Finder tags and other extended attributes, FinderInfo and resource fork on macOS; its `user.` extended attributes on Linux; its alternate data streams, such as `Zone.Identifier`, on Windows), read back and compared too, its date and permissions, then given its name, never replacing one there. A drive that can't keep an original's extras (FAT and exFAT on Linux and Windows; macOS keeps them there in `._name` files) leaves that photo where it is, and says so; what the system keeps for itself (macOS's `com.apple.provenance`, Linux's `security.` labels and access lists) isn't carried. The catalog follows a photo only once every file of it is copied and its original is still the file that was copied; only then do the originals go to the Trash. A move whose copies wouldn't fit on that drive (with 32 MB to spare) is refused before anything is copied, and so is a move to or from a network drive other than an SMB share (on a Mac, mounted as CIFS on Linux, or a network drive or `\\server\share` folder on Windows), or any other whose files RAWmakase can't tell apart (copy them in Finder, then use Synchronize Folder); a move within such a drive renames as on any other. Local APFS and HFS+ (macOS), ext2/3/4, XFS and Btrfs (Linux) and NTFS (Windows) drives keep the numbers that tell a copy from another file of its name. FAT and exFAT drives (SD cards, most external SSDs) number their files anew as they are written, renamed or plugged in again, so there a copy is told by its exact name and its bytes instead (SHA-256 of what was copied), and an original by its name, its size, date and first bytes, and, before it goes to the Trash, all its bytes again; no such number is recorded for a copy there (one no file has stands in, so an earlier release leaves such a move for you rather than act on it). An empty file found where a copy was being made, before that was recorded, is taken for the copy only when the drive says it was made after the move was planned. exFAT on macOS can't give a name only where none is, so there each copy is made at its name straight away (never replacing a file), and one a move undoes goes to the Trash. An SMB share (a NAS, or a Windows or Mac computer's shared folder), on a Mac, mounted as CIFS on Linux (`mount.cifs`), or on Windows (by drive letter or `\\server\share` path), is moved to and from as macOS's exFAT is: each copy is proven by its name and bytes and made at its name, as a share can't promise that a rename won't replace a file another computer put there. A copy a move onto a share undoes would go to the Trash, which a share hasn't got, so it stays there, even part-made or empty: nothing on a share can be removed only while it is still the copy RAWmakase checked, and another computer could put its own file at that name just then. The move is listed under **Unfinished file operations**, saying its copies were left on the share; delete them there (Put Back changes nothing while they are there), and it clears, or choose Keep as Is. It says so only while every original still holds all of its copy's bytes, and every folder a folder move left there holds nothing but its copies: a copy whose original changed meanwhile may be the only one of those bytes left, and a file another computer put in such a folder isn't RAWmakase's to have you delete, so such a move is listed as not put back instead. A Mac has no Trash on a share, and Linux's (the share's `.Trash-$uid` folder) and Windows' (a folder redirected to a share has a Recycle Bin there) are filled by a rename that can replace a file another computer put at its name, so they aren't used: photos moved off a share are copied and checked, and their originals stay where they were (nothing is deleted instead): the question says so before anything is copied, and the outcome lists them, to delete in Finder once you've checked the copies. For the same reason nothing is renamed on a share: renaming photos or folders there, or moving them within one share, leaves them as they were. A share drops an extended attribute with no value, so a file or folder with one stays where it is; on Windows, a share whose server keeps no alternate data streams (Samba without `streams_xattr`) keeps none, so a file with one (`Zone.Identifier`, say) stays where it is, and its copy there is left for you to delete. A share's listing can lag what another computer did, so a file there (as on FAT and exFAT) is taken for gone only when its folder lists no such name and looking it up finds nothing. NFS, WebDAV and FUSE shares stay refused; so do GVFS's on Linux (a desktop's `smb://` places), which keep no birth times, permissions or extended attributes and number files anew each mount: mount such a share with `mount.cifs` to move files on it. The hidden partial copy is found by its name however the drive spells it (HFS+ keeps names decomposed). A partial copy written whole is kept, never removed, while its original can't be found as it was, and a name there held by another file is never taken for the copy gone: such a move is listed for you. A drive that keeps dates more coarsely (exFAT, FAT, HFS+, NTFS) gives the copy the nearest date it can; the photo's edit and checksum then move to the copy, which has the same bytes, unless the photo still has an edit file from a release before the catalog beside it, which names the original's date: that photo stays where it is. An original the Trash can't take (a drive without one), that changed since it was copied, or whose extras aren't its copy's any more (tagged meanwhile, say) stays where it was, beside its copy, which the catalog follows, and the outcome says which and why. A copy that fails (a full drive, a file that reads back differently or changed while it was read, a name taken there meanwhile, Stop, which stops a copy between 1 MiB chunks) is undone: its partial copies are removed, its complete copies go to the Trash, and the originals and the catalog are as they were. A folder's name is refused when Windows or macOS couldn't use it, and one already there, or that the catalog has (even missing), is never taken for the new one. While photos move, the top bar counts them, with Stop. The open photo follows its file, and its edit saves there. When a catalog opens, RAWmakase finishes what a crash cut short where the files prove where they are: a move to another drive the catalog already followed has its originals put in the Trash, each only while it is still the file copied and its copy reads back the same, and one it didn't follow is undone once every original is proven where it was; what it can't decide is listed under **Unfinished file operations**, each with its files and why, to **Put Back** (renamed back where they were; for a move to another drive, its copies put in the Trash (a partial copy not yet whole is removed) while each original is where it was, even if it changed since; while one isn't, it says so and changes nothing), **Keep as Is** (Synchronize Folder can match the files later) or, for a folder made, **Add to Catalog** when it is proven the folder RAWmakase made. A folder is never deleted to put one back. **Decide Later** asks again when the catalog next opens.

**Renaming.** Press F2, or choose Rename… in the thumbnail menu. For one photo, **Rename Photo** asks its new name; the extension stays as it is. For several, **Rename Photos** names them by a Lightroom template (Custom Name - Sequence and the others export offers), with a start number and how many digits the sequence has (`Trip-001`), numbered in the order they were taken: by the capture time the catalog has (for photos added from folders, read from their files in the background after they are added; renaming reads no file for it); photos taken at one time keep the Library's order, and those without a capture time come last, by name. The order is read once when the dialog opens. As you type, the names are checked in the background, so typing never waits for them, and each photo's new name is shown with anything that stops it: a name taken there (on disk, or by a photo of the catalog, even an offline one), given twice, already another photo's in the same rename, or one Windows or macOS couldn't use. Then none is renamed; Rename is the dialog's own, and runs only when every name can be had, once what was typed last is checked. The XMP sidecars and earlier releases' edit files only a photo reads are renamed to match; a file keeps its bytes and dates, so its edit and checksum stay valid, and the open photo follows. The template's **Original filename** token, in Rename Photos and Export alike, gives the name the photo's file had when it entered the catalog (added from a folder, synchronized, or from Lightroom's `originalFilename`), without its extension, however often it was renamed since; a photo added by a release before 0.4.12 kept none, and the token gives its current name. A name that changes only in case or accents (`ROUND.NEF` to `round.NEF`) works on APFS (on a case-sensitive APFS volume, a change of case only) and is refused elsewhere for now. **Rename Folder…** in a folder's menu renames it on disk and in the catalog, with its photos and the folders in it (a folder holding only folders, such as `2024-trip` above `day1` and `day2`, too); a root folder is renamed in Finder, then located again, and a folder with a folder inside located on its own isn't renamed yet. On an NTFS drive Linux mounts with ntfs-3g (as Linux Mint and Ubuntu do), photos are renamed, but folders aren't yet.

**Moving a folder.** Drag a folder onto another folder in the Folders panel, or choose **Move Folder…** in its menu and pick where it goes (a root folder, or a folder of one: its own root's or another's). RAWmakase asks first, with how many photos move with it, Cancel focused; the folder moves on disk by one rename and the catalog follows: it stays the same folder, with its photos, the folders in it and their edits, and moved into another root folder it becomes that root's. Any folder can be moved, one holding only folders too; a root folder only into another root (below). It isn't moved into itself or a folder in it, nor where a folder or file of that name is (on disk or in the catalog, even missing), nor when a folder in it is located on its own or holds another root folder, nor into a root folder that is offline here.

A root folder can be dragged onto a folder of another root, or onto that root itself, or moved there with **Move Folder…** in its menu, as Lightroom Classic lets a top-level folder be; on the same drive or another, as a folder moves. It becomes a folder of that root, named as its folder is, with its folders, photos, edits and collections, and leaves the list of root folders; the question says so. Where it was located on other computers goes with it, and they find it in that root from then on. It isn't moved into itself or a folder of its own, nor when it holds the catalog, RAWmakase's own folders, another root folder or a folder located on its own (on any computer), nor when it is offline here or the top of a drive, nor where a folder can't go (a name taken, a destination offline, or a drive RAWmakase can't move folders to). Moving a root folder to a new place of its own, with no root to go into, is done in Finder, then **Locate root folder…**.

To another drive a folder is copied whole instead, every file in it (sidecars, hidden files and files the catalog doesn't know too), and the question says how much and that the originals then go to the Trash. It is built inside a hidden `.<name>.<run>-0-0.rawmakase-part` folder there (which Synchronize Folder and Add Photo Folder pass by), each file made where nothing has its name, copied, compared with what was read of its original (SHA-256), given its original's extras, date and permissions as a photo's copy is, and each folder its original's extras (a folder's custom icon is its FinderInfo and an `Icon\r` file with only a resource fork); then that folder gets the folder's name, never replacing anything, and the catalog follows only once every copy is proven and every original is still the file copied. Then each folder there gets its original's dates and permissions (only then, as anything made in it changes its date, and macOS won't rename a read-only folder), and when every original is unchanged, its extras still its copy's, and nothing was added beside them, the folder goes to the Trash whole; otherwise each unchanged file goes on its own, and what stays (the changed or added files, and the folders) is reported. A folder holding a link, a special file, another drive, a file with a second name (a hard link) or two names the other drive would take for one is refused, as is one that wouldn't fit there (with 32 MB to spare), and one to or from a network drive other than an SMB share, as for photos. To and from FAT and exFAT drives, and SMB shares, each copy is proven by its name and bytes as a photo's is, a folder by its name; on macOS's exFAT and on SMB shares, which can't give a name only where none is, the folder is built at its name straight away rather than in a hidden folder; a folder moved off an SMB share stays there once copied, with nothing deleted, as a share has no Trash RAWmakase uses, and the question says so; and a file's AppleDouble file there (`._name`, where macOS keeps what the drive can't) is taken as part of that file; so on macOS a folder holding a file `._name` beside `name` isn't moved onto such a drive, where it would be taken for that file's. Anything stopping the copy before the catalog follows undoes it (on an SMB share, where nothing is removed, what it copied stays and is listed for you, as for photos): still hidden, its copies and folders are removed (a copy written whole only while its original is proven unchanged; otherwise it is left for **Put Back**, which puts it in the Trash); already named, it goes to the Trash whole, and only while it holds exactly what was copied, each file read back, or it is left for the user. A drive that can't keep the extras of a file or folder in it leaves the folder where it is, and says so. **Reveal in Finder** (Show in Explorer on Windows) in a folder's menu shows it in the file manager.

**Moving a folder to the Trash.** **Move to Trash…** in a folder's menu (any folder but a root folder) puts the folder, with everything in it, in the system Trash in one go, then takes its folders and photos (their virtual copies, and copies of photos elsewhere that are in it) out of the catalog. The question counts what goes, folders, photos and other files (sidecars, hidden files and files the catalog doesn't know), names a few of the other files, and says that edits made in RAWmakase go with the photos and that catalog photos and folders in it that are missing on disk leave the catalog too; Cancel has the focus. Right before the Trash the folder is read again and has to hold exactly what was asked about (the same names and kinds, each file the same size, date and first bytes, and where the drive keeps them the same file numbers; on FAT and exFAT by names): anything added, removed or changed since stops it, and nothing moves. Only `.DS_Store`, `Thumbs.db` and `desktop.ini`, which the system writes on its own, don't count; they go too. Its root folder stays in the catalog, even with nothing left in it, as Lightroom keeps a folder when its last subfolder goes; **Remove from Catalog…** in an empty root folder's menu takes it out (its folder stays on disk). Refused: a root folder, a folder with one located on its own in it, one holding another root folder or the catalog, a link, a special file, another drive or a file with a second name inside it, a read-only drive, a network drive (macOS has no Trash on one, and Linux's and Windows' on an SMB share aren't used), any drive whose files RAWmakase can't tell apart, a drive whose Trash surely can't take it, and a folder an unfinished file operation involves. Delete and Backspace never act on a folder: they ask about the photos selected in the grid, as in Lightroom. A Trash that takes only part of the folder (possible with Windows' Recycle Bin) leaves it under **Unfinished file operations** until everything is back; after a crash that lost where the Trash put the folder, the item offers **Keep as Is** or **Remove from Catalog**; with that known, **Put Back** renames it back from the Trash. As for photos, the catalog lets the photos go only once the Trash has the folder and it is gone from its path; anything that slipped into the folder in the moment between the last check and the Trash goes with it, and the status line names it when the Trash can be read.

**Export** (Export… at the foot of the Library's left panel, ⇧⌘E, or Develop's Export button) exports every selected photo, each with its own edit, using one set of export settings; in Develop it exports the Filmstrip's selection when the open photo is part of it. Photos it can't export because they are offline are listed in the dialog before you start; a JPEG, PNG or TIFF whose pixels Develop can't read, such as a CMYK JPEG, is reported with the reason when its turn comes, as choosing the photos reads no file. With "Ask what to do", files that already exist are asked about once for the whole export. Exports run one at a time while you keep working: the top bar shows "Exporting 24 / 150", cancels the running one, and lists those waiting so they can be removed. When something was not exported, the top bar says so until you dismiss it; click the message for each photo and why. Selecting a folder or collection and pressing ⌘A selects the photos shown, so filters can leave some out. Rename To offers Lightroom's templates: Filename, Filename - Sequence, Custom Name, Custom Name - Sequence, Custom Name (x of y) and Date - Filename, with a Start Number. Sequence numbers follow the order the photos were chosen, so a photo that is not exported keeps its number; a photo without a capture date is named "undated-" rather than dated by its file. Rename To also offers RAWmakase's own templates (Date Time - Model, "2026-04-24 18.43.24 ILCE-7RM6"; Date Time - Filename; Date - Sequence) and Edit…, Lightroom's Filename Template Editor: a name built from Lightroom's tokens (Filename, Filename number suffix, Copy name, Folder Name, Sequence # and Total #, the capture date's parts, Title, Caption, Copyright, Creator, File Dimensions, Exposure, Focal Length, ISO Speed Rating, Make, Model, Lens, Rating, Label and Custom Text) and text, kept as Lightroom keeps it ("{{date_YYYY}}-{{date_MM}}…"). Model is the camera's model as its file writes it ("ILCE-7RM6"), Make the maker as RAWmakase spells it ("Sony"), as Lightroom shows them; they are read from the files in the background when a template needs them, and Export waits for them. A value a photo lacks is left out and said in the export's notes; the whole name is made a valid file name (`/`, `:`, `\`, `*`, `?`, `"`, `<`, `>`, `|` become `-`), so it can't name another folder. Lightroom tokens RAWmakase doesn't fill here (Import # and Shoot Name, which only Import Photos gives; GPS…) are kept in a template and left out with a note. Post-Processing's After Export can show the exported files in Finder (Explorer, or the file manager on Linux), one window for each folder exported to, up to five; the status line says when there were more. Its Send To, shown once an extension offers an export destination, sends each file on as it is written (a web gallery, an upload), with the photo's UUID and catalog facts and the destination's own options for this export drawn under it (a gallery's title, its layout), and the top bar says what was exported and then what was sent, file by file ([export destinations](extensions/overview.md#export-destinations)).

## Importing from a card

**Import Photos…** (⌘⇧I, Ctrl+Shift+I elsewhere; in the Library's Folders panel below Add Folder…, in the catalog menu and in macOS's File menu) copies photos from a camera's card, or any folder, into your library and adds the copies to the catalog, as Lightroom Classic's Import with Copy does. Add Folder… is still the way to catalog photos where they are; Import Photos never changes, renames or deletes a source file.

- **From**: an attached card or drive (a camera's card is offered by its `DCIM` folder, and chosen when the dialog opens) or any folder (Choose…). *Include Subfolders* (on) reads the folders inside it too. Photos are found as Add Folder finds them (the same file types, no hidden files, no symbolic links), each read once in the background: its capture time (from its EXIF, else the RAW file itself, so Fujifilm RAF, TIFF and JPEG are dated alike) and what a file name can take from it. A file that changed while it was read is read again; one that can't be read, or keeps changing, is listed with why and not imported.
- The photos show as thumbnails from their embedded previews, each with a checkbox (Check All, Uncheck All), and the count and size checked. A photo without a capture time is filed and named by its file's modification time, as Lightroom dates it, and marked **Dated by its file**; in the catalog it has no capture time, as Add Folder leaves such a photo (Lightroom records the modification time there).
- **File Handling**: *Don't Import Suspected Duplicates* (on at first; the choice is kept). A suspected duplicate, Lightroom's rule, is a photo the catalog already has by its original file name, EXIF capture time and size, online or not, and whatever it is named now (by name and size alone when a capture time isn't known on either side), or one found twice on the card. While the option is on, suspected duplicates are greyed out, without a checkbox, and aren't imported; while it is off, none is looked for and every photo checked is imported, as in Lightroom.
- **File Renaming**: keep the photos' names, or *Rename Files* by a template: the presets and saved templates of Rename Photos and Export, Lightroom's import-only *Shoot Name - Original File Number* and *Shoot Name - Sequence*, with Custom Text, Shoot Name and a Start Number for the templates that take them, and Edit… (the Filename Template Editor, which here also offers **Import #** and **Shoot Name**). *Extensions* (Leave as-is, Lowercase, Uppercase) spells a renamed photo's extension; a kept name keeps its own. A Sample line shows the first photo's new name. **Original filename** gives the name on the card, however the photo is renamed later, even when a taken name gave the copy a `-2` (Lightroom records the `-2` name there); **Import #** is the import's own number, counted per catalog (`catalog_counters`), each number used once even when an import is stopped (Lightroom's Import Number; it can't be edited in Catalog Settings yet). Add Folder and Synchronize name nothing and don't count an Import #. Image # isn't filled yet.
- **Apply During Import**: a **Creator** and a **Copyright** typed here replace what the photos' files say (the camera's Artist and Copyright, a sidecar's), and **Keywords** (comma-separated, `>` between levels, as the Keywording panel takes them) are added to the photos' own, as Lightroom's metadata preset and keywords apply them; an empty field gives nothing. They are written in the catalog, not in the copies, which stay byte for byte the card's. Metadata presets and a develop preset on import aren't offered yet.
- **Destination**: the folder, *Into Subfolder* (a folder made there that the rest goes into), and **Organize**: *By original folders* (the folder chosen as the source and those below it: `DCIM/100CANON` for a card, whose `DCIM` folder is the source; a whole drive chosen as the source can't be recreated, and its photos aren't imported this way), *By date* or *Into one folder*. By date files each photo into folders of its date in one of Lightroom's thirteen Date Formats, shown with today's date: 2026/11-19, 2026/2026-11-19, 2026/November 19, 2026/11, 2026/Nov, 2026/November, 2026/11/19, 2026/November/19, 2026/2026-11/2026-11-19, 2026-11-19, 2026 Nov 19, 2026 November 19 or 20261119. A folder pattern made of tokens (`{year}/{camera}`) isn't offered yet.
- What it would do is checked in the background as the choices change, and listed: each photo's new folder and name, the folders it makes, and why a photo isn't imported. A name already taken there, on disk or by a photo of the catalog, gets the next free `-2`, `-3`… for the photo and its sidecar files together; nothing is ever replaced. When the destination matches more than one folder of the catalog, the dialog asks which, as Add Folder… asks. The footer says how many photos, their size, the destination and the space free there. **Import** is off while nothing is checked, the destination is refused, or the space is short. A destination where a copy can't be given its name by an exclusive rename is refused, with why: an exFAT drive on macOS and an SMB network share, for now.

Import saves the open photo's edit first (if that fails, nothing is imported), then copies the checked photos, each with its XMP sidecar and earlier releases' edit files, as a move to another drive copies files: into a hidden partial copy, checked against the original, then named. Each photo is added to the catalog as Add Folder adds one (its sidecar or embedded XMP, the default Creator and Copyright from Preferences, Stack Camera Bursts), then given what Apply During Import says, with its original name, capture time and size (`photo_import_facts`), once its files are copied and checked. A RAW and the JPEG of the same shot are two photos, as Add Folder treats them. While the photos are imported, navigation, saving and every other file operation wait; the top bar shows the import with Stop, which stops after the photo being copied: what was imported stays, and nothing complete is deleted. Should the names change between the preview and the import (another import took the Import #, or a file was added there), nothing is copied and the dialog shows the new names to import again. When it ends, Previous Import shows what was added, and the top bar lists what wasn't and why (it changed since it was read, the card was removed, the disk is full, a copy didn't match, it was already imported). The dialog's choices are kept for the next import in `import-copy.json` beside `import-options.json`, with what a later release adds to it kept as it is.

An import is journalled as file operations are (`import_copy` items): a crash or a pulled card leaves it to recovery, which goes on copying while the original is still there and the same file, never removes a copy written whole, and otherwise offers only **Keep as Is** (the copies stay where they are, for Show in Finder; there is no Put Back for an import). Add Folder and Synchronize leave out the files an unfinished import is copying, so neither adds a half-imported photo.

## Stars, picks and color labels

The selected photo has clickable stars, Pick/Reject/Unflag controls and a color-label menu in both Library and Develop. Grid thumbnails use Lightroom-style gray cells, muted label-colored backgrounds, thin dividers, black photo borders and a lighter selection outline. Stars, pick/reject status and a bordered color swatch appear beneath the photo. Right-click a thumbnail for Set Flag, Set Rating and Set Color Label (all five colors and None). The Library label filter includes imported custom text as well as the five standard colors. Changes save immediately to the RAWmakase catalog, work for offline Library photos, and remain independent for virtual copies. Changing metadata never changes the RAW, its sidecars or the Lightroom catalog.

| Key | Action |
|---|---|
| 1–5 | Set that many stars |
| 0 | Clear stars |
| [ / ] | Decrease / increase stars, bounded to 0–5 |
| P / X / U | Pick / reject / unflag |
| Backtick | Toggle pick / unflag |
| 6 / 7 / 8 / 9 | Toggle Red / Yellow / Green / Blue |
| Shift + rating, flag or color key | Apply and advance in the current filtered order |
| Left / Right | Previous / next photo; in Develop, past photos it can't open |
| Z | Toggle Fit / 100% zoom in Develop |

Purple and **No label** are available in the menu. Repeating a color shortcut clears that same label; ratings set an explicit number, with 0 clearing them. Clicking the currently selected star clears the rating. Shortcuts are suppressed while editing text or numbers, during dialogs and during export; modified system shortcuts such as Command+X are not intercepted. `1` now means one star, replacing its previous zoom shortcut.

The importer reads Lightroom `rating`, `pick` (−1 rejected, 0 unflagged, 1 picked), and `colorLabels`. Missing ratings/flags become zero; missing labels become empty. Label text is preserved exactly, including custom/localized names. Standard Lightroom label names map to the corresponding color. Other text displays white and remains searchable/filterable; a custom Lightroom label-set mapping is not reliably available from a standalone `.lrcat`, so RAWmakase does not guess its color. No write-back/synchronization with Lightroom is performed. In the Grid, rating, flag and label keys apply to every selected photo. Each change is one step that Cmd+Z undoes and Cmd+Shift+Z redoes, in the same undo sequence as Develop; it is kept in memory and cleared when another catalog opens. Caps Lock auto-advance is not implemented.

Shortcut reference: [Adobe Lightroom Classic keyboard shortcuts](https://helpx.adobe.com/lightroom-classic/desktop/introduction-to-lightroom-classic/keyboard-shortcuts.html).

## Import and preservation

The importer takes a private snapshot of the source, checks its SQLite structure/integrity, and imports in one transaction. It requires a closed/exported catalog without a nonempty WAL/journal; it refuses an active/incomplete copy rather than ignoring pending changes. The importer has no size limit and was exercised on the supplied Lightroom v13 catalog. Incompatible layouts fail without leaving a destination file.

Normalized tables retain images and virtual-copy identities, original paths, folder roots, capture dates, ratings, flags, color labels, collections/memberships, keywords/parents/memberships, serialized Develop settings and Develop history steps (the `lightroom_history` table, shown under **From Lightroom** in the History panel, where each step can be applied). Imported collection sets, collections and smart collections can be browsed in the Library's Collections panel; smart collections list the photos their rules match now (see Smart collections below). The Quick Collection (B, Cmd+B, Cmd+Shift+B) is the only collection whose photos can be changed. Keywords can be added and removed in the Keywording panel, for every selected photo, as one undoable step. Lightroom's hidden root keyword, a nameless one its top-level keywords are under, is imported as it is but never shown, searched or exported: a typed top-level name is found under it, and a new top-level keyword goes under it, as in Lightroom. Develop snapshots, folder stacks, photo info (camera, lens, exposure, dimensions), descriptive metadata from each photo's XMP (title, caption, creators, copyright, location) and keywords' export options are imported too.

The new catalog is canonical: an import reads the `.lrcat` once, and nothing in the `.rawmakase` file depends on it afterwards. What the importer doesn't interpret is not kept: faces, publish services, the GPS and IPTC fields the metadata copy doesn't read, and anything a later Lightroom adds stay in the user's `.lrcat` only. The `sources` table records the path the catalog was imported from and its size. External `.lrcat-data`, preview bundles, originals and profiles are not embedded or synthesized.

Earlier releases kept a byte-exact copy of the `.lrcat` in `sources.original_catalog` and read it again on later opens to add what newer releases import. The first open by this release empties that copy, in one transaction recorded as `lightroom_archive_removed` in `meta`, and then compacts the file once ("Making the catalog smaller…") to give the space back. Compacting needs free space up to the catalog's size; when it fails, the catalog opens anyway, the status line says why, and `compact_pending` in `meta` has it tried again on the next open. The format doesn't change: an older release reads the empty copy as nothing to read. A catalog imported by an older release keeps everything it already copied, including History and snapshots stored compressed.

## Descriptive metadata and XMP sidecars

Title, caption, creators, copyright, capture time, location and keywords are kept per photo in the catalog; a virtual copy has its own once created. A field with no value in the catalog is the file's own (its EXIF, at export); a cleared field leaves the file's out too.

**Lightroom import** reads each photo's title, caption, creators, copyright, capture time and location from the XMP Lightroom keeps in its catalog; keywords, ratings, flags and labels come from Lightroom's own tables. Catalogs imported before this read it once when opened.

**Add photo folder** reads, for each new photo, its XMP sidecar and, for JPEG, TIFF, PNG, WebP, AVIF, HEIF, JPEG XL, DNG and Canon CR3, the XMP inside the file (title, caption, copyright, creator, capture time, location, keywords and rating; the camera comes from the file's EXIF). A CR3's is the XMP the camera writes, so a rating given in the camera comes with the photo, as in Lightroom; the XMP inside other proprietary RAWs (ARW, NEF, RAF and others) is not read. A JPEG XL's metadata boxes are read also when brotli-compressed ("brob"), as cjxl writes them by default. A RAW's sidecar is `IMG_1234.NEF.xmp` (digiKam's default), else `IMG_1234.xmp`; when both exist the first is used and the other is listed as ignored. `IMG_1234.xmp` beside both `IMG_1234.NEF` and `IMG_1234.JPG` is the RAW's; the JPEG reads only `IMG_1234.JPG.xmp` and its own XMP, field by field, the sidecar's winning, and an explicitly empty sidecar value clearing the field. Sidecars that can't be read are counted in the top bar; click the message to list them. Adding a folder again does not read the sidecars of photos already in the catalog. Each new photo is written together with its metadata, its default Creator and Copyright and any edit an earlier release saved beside it, so a failed write (a full disk) leaves none of the folder's new photos, and adding the folder again adds them complete.

**Read Metadata from Files…** (thumbnail menu) does, for the selected masters: every field a file has replaces the catalog's, your edits included; fields the file lacks are kept. It asks first, is one step for Undo, and never reads into virtual copies.

Keywords are read from `lr:hierarchicalSubject` ("|" between levels), else `digiKam:TagsList` ("/"), then any `dc:subject` name no path has, as a top-level keyword; with neither, `dc:subject` is flat keywords. digiKam's color labels map to Lightroom's names (red, yellow, green, blue, purple; others by their color name) and its pick labels to picks and rejects. What can't be reconstructed: a name containing "|" (or "/" through digiKam) read from another tool's file becomes a hierarchy; a top-level keyword named like an element of a hierarchy, in a file without a path for it, merges into that hierarchy; the parents of a keyword with "|" in its name are lost on a round trip.

**GPS from the camera.** A photo added from a folder (Add Photo Folder, Synchronize Folder, Import Photos) whose sidecar and own XMP give no location takes the one its camera wrote in its EXIF (the GPS directory: latitude and longitude by their N/S and E/W references, and the altitude above or below sea level), as Lightroom reads it. It is read in the background after the photo is added, with its capture time and from the same read of its EXIF, so adding a folder opens no file for it; the Metadata panel and the map show it once read. Only a photo the catalog has no location for gets it: a sidecar's or the file's XMP location, which is newer, wins, one removed meanwhile stays removed, and a photo whose sidecar can't be read gets none, as the sidecar may hold one (only a photo whose EXIF has a location has its XMP read again to tell). A virtual copy made before then gets it with its master, as it gets the capture time. This read isn't a change of yours, so it isn't a step for Undo, and undoing or redoing a change that left the location alone (a title typed before it was read) keeps it. Only photos added from files get it this way: a photo imported from a Lightroom catalog has the location Lightroom keeps, which Lightroom read from the file when it imported it, so none there means none, even where the file has GPS (removed in Lightroom, say). The EXIF is read where RAWmakase reads a camera's EXIF: JPEG, TIFF, PNG, WebP, AVIF, HEIF and JPEG XL files, TIFF-based RAWs (DNG, NEF, ARW, CR2, ORF, RW2, PEF and others), a Fujifilm RAF's preview, and the CR3, MRW and X3F files RAWmakase's RAW decoders read. A position of zeros (written before the camera has a fix), references without coordinates, unknown (0/0) or out-of-range values give none. Photos added before this release had their files read already and don't get it on their own: **Read Metadata from Files** fills it, by the same rules and in the same step as the rest it reads, for any photo you ask it of, one imported from Lightroom included, as it reads the file's other values. An export writes the file's GPS directory whole (its time, direction and other tags) while the photo's location is still the one read from it.

Not read or written: IPTC location and contact fields, headline, credit, source, usage terms, instructions, people and face regions, other digiKam data, ratings in other namespaces, XMP history and unknown namespaces. Sidecars are never written. A virtual copy created by RAWmakase 0.1.12 or older has no values of its own and uses the file's until edited.

## Keywords

The keywords of a catalog are shared by all its folders. In the Keywording panel (Library, right panel), type keywords separated by commas: `Child < Parent` for a hierarchy, or `Parent > Child`, or `Parent|Child`. A typed name is found as Lightroom finds it: at any level, ignoring case; among several, the one in the same case, then one at the top level, then the first made. A typed hierarchy finds its top name the same way and each name below under the one above it. A name not found is made, in the case typed, at the top level. While typing, the catalog's keywords matching the name are suggested at any level, as `Child < Parent`; ↓ and ↑ choose one, Tab or Return takes it, and the keyword taken is the very one shown, even beside another of the same name.

**Keyword Set**, under the field, holds nine keywords laid out as a numeric keypad (7 8 9 on top). A button shows whether the selected photos have its keyword; clicking it removes the keyword when they all have it, else adds it to all of them. ⌥1–⌥9 click them (not while typing in a field), and ⌥0 / ⌥⇧0 show the next or previous set. **Recent Keywords** holds the nine keywords most recently given to a photo in this catalog, the latest on the top row. A set's slots are typed keywords, found and made as typed ones are, so a set made for one catalog works in any other. Sets are `.lrtemplate` files, as Lightroom saves them, in the data folder's `Keyword Sets`; Lightroom Classic's sets (`~/Library/Application Support/Adobe/Lightroom/Keyword Sets` on macOS, `%APPDATA%\Adobe\Lightroom\Keyword Sets` on Windows) are listed too and never changed: saving over one saves RAWmakase's own of that name, listed in its place. Lightroom's Outdoor, Portrait and Wedding Photography sets come built in. The menu has New Keyword Set… (a name and nine slots typed at once), Save Current Settings as New Preset…, Update Preset, Rename, Delete (RAWmakase's own sets only) and Edit Set…, whose changes show the set as edited until saved.

**Keyword List**, below, lists every keyword as a tree with how many photos have it, and filters it by name. Each box shows whether the selected photos have the keyword (a dash when only some do); clicking it adds or removes it for all of them. The arrow shows every photo in the catalog with the keyword (All Photographs, with the keyword chosen in the Metadata filter). There, and in the Metadata filter's Keyword column and the Library's search, a keyword is named by its path (`Paris < France`), so keywords of one name under different parents are told apart, and a filter that chose one keeps it when other keywords are made or deleted. A filter kept from an earlier release, which chose keywords by name alone, chooses every keyword of that name. Right-click a keyword, or use the ⋯ menu, to create a keyword (inside it or at the top level), rename it, delete it or purge the keywords no photo has. Deleting a keyword deletes the keywords inside it and takes them off their photos, asking first when a photo has one or there are keywords inside, as Lightroom does. A name its parent already has, ignoring case, is refused, and nothing is merged. Each is one step for Undo, which puts back the keywords as they were, with their export options and their photos.

## Lightroom rendering

A photo without a RAWmakase edit opens with its Lightroom edit applied, once camera profiles are known. **Apply compatible Lightroom edits** re-applies it as one undoable change using RAWmakase's supported controls. It parses Lightroom's serialized settings as data, never as executable Lua. Lens corrections, Transform and Upright (from Lightroom's stored corrections) apply. It reports missing profiles and unsupported controls, such as AI and color-range masks, Glow and Reshape. A look's Profile Amount applies to looks that support it ([Profile Amount](lightroom-profiles.md#profile-amount)); an Amount outside 0–200% is reported and renders at 100%. Spot removal, red eye corrections and brush, gradient, radial and luminance-range masks convert to RAWmakase's experimental spots, red eye (and Pet Eye) corrections and masks. Compatible controls use RAWmakase's algorithms; this is not a Lightroom appearance guarantee. The untouched original settings remain in the database even after further editing. Lightroom orientation metadata is preserved; current previews/Develop use the source camera orientation.

## Relinking offline photos

On Linux, Lightroom's `/Volumes/...` and `/Users/...` paths will often be offline. Click the **…** on a root row, or right-click it and choose **Locate root folder…**, to map a complete source root to its local directory. The **Browse…** button opens the native directory picker for the selected tree folder; choosing a directory applies the mapping, and Cancel leaves it unchanged. After relinking, RAWmakase reports the available photo count. Right-click a folder and choose **Locate this folder…** for a narrower mapping; a folder holding only folders (such as a shoot's folder above its `RAW/Card 1` folders) can be located too, and every folder below it follows. Descendants inherit a folder mapping; a more specific mapping takes precedence. In the Folders panel a folder located on another drive shows under that drive, after its root folders, with the folders in it; its root folder still counts its photos and shows them when chosen, as they are still in it. Paths are changed only in the RAWmakase catalog. Files are never moved, renamed or matched by filename alone.

When only some photos moved, or moved somewhere the catalog doesn't know, right-click an offline photo and choose **Find on Disk…** (also in Develop's **Photo** menu for the photo open there; for a virtual copy it finds its master). The file picker starts in the nearest folder of the photo's old place that is still there. Pick its file: RAWmakase checks it against the checksum on record and refuses a file whose size, quick hash or full checksum says it is a different photo. Then it looks in the same folder (not its subfolders) for the other offline photos of the photo's catalog folder. A file whose full checksum matches is ticked; one that matches only by its quick hash, or by the file its edit was saved for, is **probably** that photo, and one with the same name, for a photo without a checksum, is offered **not verified**: both start unticked. The review is titled `Found 8 other missing photos in this folder`, and **Relink 9 Photos** updates their catalog rows, so ratings, flags, keywords, collections, metadata, edits, History, snapshots and virtual copies stay with them. When only the file picked is found, verified, it is relinked straight away and the top bar says `Relinked 1 photo`. A file picked without a checksum to verify it is still taken, as you chose it; its edit follows it only when it is the same photo, as after a probable move. A folder no catalog folder covers is added as a new root folder, holding only the photos relinked into it: Add Folder or Synchronize adds its other files later. A folder that holds root folders of the catalog, or that another location of the catalog claims, is refused. If the photo's old drive isn't connected, only a verified match is offered, and the review warns that the catalog uses the file found from now on, even if the old one is still there. The photo open in Develop follows only a verified match, its unsaved edit kept and saved at the new place; for any other file picked, open another photo in Develop first. Find on Disk adds no photos, so Previous Import stays as it was. `rawmakase find-photo CATALOG PHOTO_ID FILE [--apply]` does the same from the command line.

## One catalog on several computers

RAWmakase reads a checksum of every master photo's file in the background, so that a photo moved or renamed outside RAWmakase can be found again: a quick hash of three 64 KiB blocks for every photo first, then the SHA-256 of the whole file, one file at a time and at most 64 MB/s. Reading waits while an export runs, previews are built or Develop opens a photo. A checksum is kept only while the file is unchanged, and is read again when it changes; a virtual copy has none of its own, and Set Copy as Master hands its master's over. **Preferences › Catalog** shows how many photos have one and can pause reading them. Nothing is written beside the photos.

## Synchronizing folders

**Synchronize Folder…** (right-click a folder or root in the Folders panel, or the Catalog menu for the folder selected) and **Synchronize All Folders…** (Catalog menu) bring the catalog back in line with files changed outside RAWmakase. A photo moved or renamed keeps its catalog row, so its rating, flag, label, keywords, collections, metadata, Develop edit, History, snapshots and virtual copies stay with it. Nothing on disk is moved, renamed or deleted.

The scan runs in the background while the Library and Develop stay usable; the top bar shows `Synchronizing "Lisbon" · 1,240 files` with a stop button. Each folder is looked for where it is on this computer, and a photo counts as missing only when its folder was listed and lacks it (or the folder is gone from a location that is there and online); an offline folder or volume is listed under Not checked, never as missing. Files no photo names are matched with the checksums on record: a file whose full checksum equals a missing photo's is that photo, moved; one that matches only by its quick hash, or by the file its edit was saved for, is **probably moved** and left unticked; a byte-for-byte copy of a photo still there is offered unticked under **Add copies…**; several candidates are left for you to pick from.

When the scan finishes, **Review synchronization** opens automatically in Library or Develop once any other dialog has closed. Moved photos and new files start ticked; probably-moved photos, copies and **Remove missing photos** start unticked. Removing photos that hold edits, ratings or copies asks first. Applying checks every action again and skips anything that changed since the scan; the top bar reads `Synchronized · 14 updated · 32 added · 5 still missing`, with the details on hover. A moved photo's edit opens on its new file when that file is the photo the edit was saved for: the same size and first 64 KiB, whatever its modification time; otherwise it stays protected, as it was. The photo open in Develop follows a verified move of its file, its unsaved edit kept and saved there. New photos get their sidecar metadata, legacy edits and default Creator and Copyright as Add Photo Folder gives them, and become **Previous Import** (Catalog section), which holds the photos the last Add Photo Folder or Synchronize added; after a synchronization that added photos, the status bar offers **Show**.

`rawmakase sync-folder CATALOG [FOLDER] [--apply]` prints the same plan from the command line, and applies what the review ticks by default with `--apply`.

Each computer keeps its own location for the catalog's folders, so a catalog taken from a Mac to a Linux machine (and back) finds its photos on both, even when the NAS is mounted at `/Volumes/Photos` on one and `/mnt/nas/photos` on the other. Locating a folder only changes where it is on the computer you're using. **Preferences › Catalog › Folder locations** lists every root with its location on this computer ("as added" when it has none), whether it is found, and the folders below it located separately, each with **Change…** and **Clear**. Clearing a folder makes it follow the nearest location above it; clearing a root makes it use the path it was added with and keeps its folders' own locations. Changing a root or a folder that has such folders below it asks whether to keep them or clear them. Other computers' locations are shown for reference, and **Find Missing Folder** starts where another computer has the folder when that path exists here too. A location that is offline stays offline: RAWmakase never falls back to another path.

Each install has a random computer id, kept in its local data folder (never in the catalog or a synced folder); the computer's name is only a label and can be changed. The first time a computer opens a catalog with this release, it copies the catalog's existing mappings as its own, so nothing moves.

Adding a folder matches every folder found on disk, the one you chose and every one below it, with this computer's locations. A folder another location already covers joins that catalog folder, so adding the same share on a second computer adds no new root and no duplicate photos. A folder whose catalog folder is located elsewhere on this computer (an old copy left behind after locating it somewhere else) is skipped and reported. When two catalog folders match equally, RAWmakase asks which one it is. Folders added on Windows now resolve on macOS and Linux; a Unix folder name containing `\` stays one name, and is unavailable on Windows.

Older releases still open the catalog: they read and write a single mapping for all computers, as before, and the newer release writes that mapping too. Their changes don't move folders on a computer that has already opened the catalog with this release, and a root they add is found where it was added until it is located there. A folder located while the catalog has no folder of its own for it (one holding only folders) isn't seen by them: they find the folders below it through their own locations, else their root's.

Keep only one computer using a catalog at a time: close it on one before opening it on another. SQLite over a network share isn't safe for two computers writing at once.

## Editing in another program

Edit In opens a photo in another editor, as Lightroom's Edit in Photoshop does.
Add the programs in **Preferences > External Editing** with **Add Editor…** (an
application on a Mac, a program file on Windows and Linux); the first one in the
list opens with **Cmd+E** (Ctrl+E on Windows and Linux), and **Move Up** changes
which one that is. Nothing is looked for on the computer: only the programs added
there are offered.

Right-click a photo in the grid or the filmstrip and choose **Edit In**, or use
Develop's Photo menu, Photo › Edit in External Editor on a Mac, or Cmd+E. Edit In
takes the photos Export would: the selection in the Library, in Develop the
filmstrip's selection when the open photo is in it, else the open photo. For each
RAW photo RAWmakase saves a 16-bit TIFF with its edit beside the original, named
`DSC_0001-Edit.tif` (`-Edit-2` and so on when that name is taken), in the color
space chosen on the same page (ProPhoto RGB unless you choose Adobe RGB or sRGB).
The TIFF is added to the catalog on top of a stack with its original (Undo takes
the stack back) and opened in the editor. As in Lightroom, it takes the
original's place: selected instead of it, and open in Develop when the original
was, so the photo shown is the one being edited. The TIFF carries the photo's metadata
but not its develop settings, which are in its pixels. Your last export's settings
are left as they were.

A JPEG, PNG or TIFF (any photo that isn't a RAW, an Edit In TIFF included) can be
opened as it is, so RAWmakase asks first, as Lightroom does, once for all of them:

- **Edit Original** (the default): the file itself opens in the editor. Nothing is
  copied or added, so editing an Edit In TIFF again makes no new file.
- **Edit a Copy**: the file is copied as it is beside the original
  (`IMG_0001-Edit.jpg`, `-Edit-2` and so on), added on top of a stack with it and
  opened.
- **Edit a Copy with RAWmakase Adjustments**: a 16-bit TIFF with the edit, as for
  a RAW.

With the first two, adjustments made in RAWmakase are not in what the editor
shows; the window says so when the photo has some. RAW photos chosen with them
are always edited as a TIFF with their adjustments.

While files are open in an editor, RAWmakase follows them, whether its window is
in front or not (on a second screen, say): the system tells it when something in
their folders changes, and on drives that don't say (a network share changed from
another computer) it looks at them itself every 5 seconds. Nothing runs while the
files rest. When the editor has saved one and the file has not changed for a third
of a second, its thumbnail and previews are made again, the ones shown staying
until the new ones are ready, and the photo is opened again if it is the one
shown: under a second after the save for a 100 MB TIFF. An edit made to the file
in RAWmakase stays with it, as do changes not saved yet in Develop. An editor that
saves by deleting the file and writing it again is followed through the moment
it is missing. While the catalog is busy (an import, a folder change), a save is
tried again each second for half a minute, then at the next save.

A file is followed until RAWmakase quits, another catalog opens, its photo leaves
the catalog or no longer is that file, a save to it can never be taken up for one
of those reasons, or its folder can't be watched (said in the top bar).

## Unused masks and patches

Mask rasters and AI Remove patches are stored once each, by content, in the `bitmaps` table, and a patch is a few MB. When a spot is deleted, a selection or a generation is replaced, or a photo is removed, its rasters stay for a while. Opening the catalog for use (the app or the command line) a week or more after it last did (`rasters_checked_at` in `meta`) looks through every edit, Lightroom setting, spot or mask, History state, snapshot and virtual copy, a few rows at a time, and in one transaction deletes the rasters none of them named at this look or the one before (`rasters_unnamed` in `meta` lists the ones unnamed last time), so a raster goes one to two weeks after the last thing naming it. The time is read and recorded under the write lock, so two windows opening the catalog at once look once; a last look recorded after the current time (the clock set back) or unreadable starts the week again, deleting nothing. The wait is for what no row records, such as another window's Undo back to a deleted spot. A raster is kept if its id appears anywhere in those, whatever release wrote them (an id of a shape this release doesn't know, as it is); every raster is kept when a History can't be read, and the catalog is left alone when it has a table a later release added. Looking through means inflating every History (about half a second for a hundred well-edited photos), which is why it isn't done on every open. When that leaves 32 MiB or a quarter of the file free, the file is compacted ("Making the catalog smaller…"), with `compact_pending` retrying a compaction that failed. A raster is stored in the transaction of the edit that names it, so one a save is storing is never deleted; one another window deletes while this one still holds its pixels is stored again by the next save that names it, and one whose pixels are gone from both leaves that save refused as naming a missing raster. The format doesn't change, and an older release reads a catalog with fewer rasters as it read it before.

**Smart collections** (issue #998) are evaluated, never stored as membership: Lightroom keeps none either. A Lightroom import reads each one's rules (`AgLibraryCollectionContent`, module `ag.library.smart_collection`, a Lua table literal read by a bounded parser and never run), every collection's sort (`sortType`, `sortDirection`), the target collection (`Adobe_variablesTable`'s `targetCollection`, `qc` for the Quick Collection) and the keywords' synonyms (`AgLibraryKeywordSynonym`). Rules are kept in `smart_collection_rules` in RAWmakase's JSON form, with Lightroom's text verbatim beside it, so a rule this release can't read or evaluate is never lost. A smart collection lists the photos and virtual copies its rules match, each copy with its own rating, flag, label and metadata, worked out in the background for the catalog as it is and the local day (about 0.3 s at 100,000 photos), again after every change a rule can see: ratings, flags, labels, metadata, keywords, collections, edits saved here or by Sync, presets, Auto, its Undo or an extension, photo info read in the background, photos added, removed, moved or renamed, and when the day changes. Until then it shows the photos it had and says it is updating, and Select All and Delete Rejected Photos wait. Changes another process makes to the open catalog (the command line's `sync-folder --apply`, `relink-catalog`, `find-photo --apply`, an MCP host) are seen, as for every list the Library shows, once the catalog is read again.

**Create and edit smart collections** with **New Smart Collection…** (Catalog menu) and **Edit Smart Collection…** (a smart collection's menu in the Collections panel, or double-click it), as Lightroom's dialog: a name, an optional collection set, Match all, any or none of the following rules, and the rules, each a field, an operation and a value. ⌥-click (Alt) on a rule's + adds a nested group (All, Any or None of the following are true). Only fields RAWmakase evaluates are offered, in Lightroom's menu sections; values are kept as Lightroom keeps them (a label color's number, a shutter speed's APEX value), so the rules read the same in Lightroom. A rule RAWmakase can't evaluate, from an import, is shown and can be removed; rules whose text can't be read are shown as Lightroom wrote them until new ones are saved. Saving new rules is one step for Undo. A catalog made with New Catalog starts, as Lightroom's does, with a "Smart Collections" set holding Lightroom's six: Colored Red, Five Stars, Past Month, Recently Modified, Video Files and Without Keywords, with Lightroom's own text for their rules; a catalog imported from Lightroom has Lightroom's instead.

Rules follow what Lightroom Classic 15.6 was measured to do: text is compared case aside; contains finds any word of the value inside the field ("red" finds Fred and red-car), contains all every word, contains words whole words only, doesn't contain none (an empty field matches), starts with and ends with look at each word of the field; Keywords match their ancestors, synonyms and keywords left out of export; Folder matches the whole path; Collection matches static collections' names, never smart ones', so rules can't refer to each other; Rating 0 is unrated; dates are calendar days in local time ("in the last 1 days" is today and yesterday), weeks start on the region's first day (Sunday on Linux, which isn't asked); Shutter Speed and Aperture hold APEX values (1/100 sec is 6.6438561897747). Fields RAWmakase answers: Rating, Pick Flag, Label Color, Label Text, Folder, Collection, Filename, Copy Name, File Type, Capture Date, Edit Date, Camera, Lens, Focal Length, Shutter Speed, Aperture, ISO Speed Rating, Title, Caption, Keywords, Creator, GPS Data (from a location the catalog keeps or cleared), Has Adjustments, Cropped, Treatment, the uncropped sizes and Megapixels, Aspect Ratio, Any Searchable Metadata (title, caption, copyright, creators, keywords, label, camera and lens) and Any Searchable Text (those and the file name, copy name, folder path and collections). A smart collection with a rule RAWmakase can't evaluate (Has Likes, publish services, the cropped sizes, fields the catalog doesn't keep such as City or Job, a DNG's compression, or text that can't be read) shows a warning, lists **no photos** and says why, rather than a partial match; an import says how many there are.

Known differences, until measured: words are split at white space only (and a folder path at its separators), punctuation stays part of a word and accents aren't folded; several words in starts with or ends with must each begin or end a word; a photo without a capture date (or edit date, the photo info a numeric rule asks about, or a GPS location the catalog keeps or cleared, such as one added from a folder whose file has GPS) matches no rule on it, "is not" included, and a date after today is in the last of any period; Label Text and "is" on Camera, Lens and Creator compare the whole text, case aside; Has Adjustments is any saved edit, here or in Lightroom; Cropped and Treatment come from RAWmakase's edit, else Lightroom's `HasCrop` and `ConvertToGrayscale`; File Type is read from the extension; the Quick Collection's name isn't matched by Collection rules.

Synonyms are kept in `keyword_synonyms`. Catalogs imported from Lightroom before smart collections were supported have no rules, sorts, target or synonyms; import the `.lrcat` again to get them. Earlier releases also recorded `meta` `keyword_synonyms` (`complete` or `missing`); it is no longer read and is left as it is.

Export as Catalog keeps smart collections, whatever photos go, with their sets and rules (Folder and Collection rules then see what the exported catalog has), keeps `meta`, and leaves out the synonyms of keywords it leaves out.

**Collections** group photos from any folders, as Lightroom Classic's do (issue #998). **Create Collection…**, **Create Collection Set…** and **Create Smart Collection…** are at the foot of the Collections panel and in a row's right-click menu, which makes the new one in that set (beside a collection, in its set); making a smart collection is one Undo step too. Create Collection asks for a name and the set to put it in; with photos selected it offers **Include selected photos** (on) and **Make new virtual copies** (off), which puts new virtual copies of them in instead (the copies stay when the collection is undone, as making copies isn't undoable). The right-click menu also has **Rename…** and **Delete…**, which asks first; deleting a set deletes everything in it, as Lightroom does, and photos always stay in the catalog. Drag photos from the grid onto a collection to add them, or choose **Add to Collection** in the thumbnail menu. **Remove from Collection** in the thumbnail menu (**Remove from Quick Collection** in the Quick Collection), or Delete, takes the selected photos out of the collection shown and out of it only: they stay in the catalog and in their other collections, and a virtual copy comes out without its master or other copies. Neither takes photos out of a smart collection, a set or a saved print, book, slideshow or web gallery, and the menu doesn't offer it there or in a folder. Drag a collection or set onto a set to move it there, or onto **Move to the top level**, shown while one inside a set is dragged; a set can't go inside itself. Selecting a set shows every photo of the collections inside it, smart collections and nested sets included, each once, as Lightroom does. Smart collections take no photos by hand: photos aren't dropped on them, and Add to Collection doesn't list them. Every one of these is one step Undo and Redo take back and make again; collections imported from Lightroom are changed like any other, and nothing is written back to the `.lrcat`. Lightroom's own dialog wording for deleting a set wasn't measured; the question here names how many collections and sets go with it.

**B** adds the selected photos to the **target collection**, or takes them out when they are all in it, as Lightroom's B does. The target is the Quick Collection unless another is chosen with **Set as Target Collection** in a collection's right-click menu or **Set as target collection** in Create Collection; the panel marks it `+`. Set as Target Collection in the Quick Collection's own right-click menu gives B back to it, and so does deleting the target. The target is kept in the catalog, as Lightroom keeps it in its own. **Save Quick Collection…** (⌘⌥B, or the Quick Collection's right-click menu) makes a top-level collection of its photos, with **Clear Quick Collection After Saving** on by default; saving and clearing are one Undo step. ⌘N opens Create Collection in the Library. A photo in any collection, the Quick Collection included, shows the collection badge at the right of its cell's footer, as Lightroom Classic 15.6 shows one (not for a photo only a smart collection matches); clicking it, or **Go to Collection** in the thumbnail menu, lists those collections and shows the one chosen.

A collection has its own sort, as in Lightroom: Capture Time until another order is chosen for it (what Lightroom Classic 15.6 gives a new collection), and the order chosen while it is shown is kept with it (`collection_options`, as Lightroom's `sortType` and `sortDirection` strings, each measured: `captureTime`, `addedOrder`, `touchTime`, `rating`, `pick`, `labelColor`, `colorLabels` for Label Text, `fileName`, `extension`, `aspectRatioCache`, `positionInCollection` for Custom Order; `ascending`, `descending`). A collection imported in one of Lightroom's orders RAWmakase hasn't (Edit Count, Pixel Dimension, File Type, City, State, Country, Aperture, Focal Length, Shutter Speed, ISO Speed) shows in Capture Time, its stored order left as it is until another is chosen. The folders keep their own order, back when the collection is left. A set shows in the folders' order. In Custom Order, dragging photos in the grid puts them where they are dropped, before the photo under the pointer or after it on its right half, as one Undo step; the collection's photos are numbered 1, 2, 3… in their new order. Lightroom's own numbers (`---0`, `---1`…) are read by number and photos it left without one come after the others; the numbers Lightroom writes when photos are dragged weren't measured. Custom Order is offered only for plain collections, not for smart collections, sets or folders.

Collections and collection sets are stored as Lightroom stores them (issue #998): rows in `collections` with Lightroom's `creationId` as their kind (`com.adobe.ag.library.collection`, `com.adobe.ag.library.group` for a set, `com.adobe.ag.library.smart_collection`), and each collection's photos in `collection_photos` with their place in its custom order (`position`: Lightroom's `---0`, `---1`… or none, which RAWmakase reads by number, and plain numbers it writes, a photo added going after the last). A name is unique among one set's children (or the top level's), exactly as typed, as Lightroom's "That name is already in use." has it; the same name in another set is fine. Older releases take any plain collection named exactly `quick collection` for the Quick Collection, so no collection RAWmakase creates or renames gets that name (Export as Catalog names its collection `… (export)` instead), and the Quick Collection itself can't be renamed, moved or deleted. A `quick collection` an imported Lightroom catalog already had inside a set stays as Lightroom had it. Only plain collections take photos: not sets, smart collections or Lightroom's saved prints, books, slideshows and web galleries. Deleting a set deletes everything in it; photos stay in the catalog. A new virtual copy joins collections as Lightroom Classic's does (measured in 15.6): the Quick Collection when its photo is in it, and the collection being shown when its photo is in that one, right after its photo in the custom order; never its photo's other collections, and afterwards its collections are its own. Collection ids are never given out again (`collection_id_high` in `meta`), so Undo can put deleted collections back under their ids. A collection's sort is kept in `collection_options` as Lightroom's `sortType` and `sortDirection` strings, written only when one is chosen; the target collection (B's) is `target_collection` in `meta`, the Quick Collection when it is missing or names a collection that is gone. `collection_options`, `smart_collection_rules` and `keyword_synonyms` are new without a format change, and older releases read the catalog as before (smart collections stay hidden there), but their Export as Catalog refuses a catalog this release has opened, as it refuses any table it doesn't know; export it with this release.

## Photo UUIDs

Every photo and every virtual copy has a UUID of its own (`photo_uuids`): a random version 4 UUID, lowercase and hyphenated, made in the transaction that adds the photo. It is never changed and never given to another photo, so it is the id an extension keeps or gets back after a session (a web gallery's picks, days later); the integer photo id is not: this release never gives a removed photo's id to another ([below](#sqlite-format-versions-1-to-7)), but a release before it may, and two copies of a catalog hand out the same ids to different photos. A virtual copy gets a new one, never its master's, and Set Copy as Master leaves each UUID with its row, as the edit and the rating stay, while the file's data moves to the new master. Photos imported from Lightroom get random UUIDs too: Lightroom's own `id_global` is not taken.

Copies of a catalog file share their UUIDs, and Export as Catalog keeps them: those are the same photos, and in the copy a UUID finds the copy's photo. A future import from another catalog decides what two catalogs holding one UUID mean; today nothing joins catalogs. The table is new without a format change. Releases before it ignore it, and its rows go with their photo in every release (`ON DELETE CASCADE`, with foreign keys on at every open). Photos they add have no UUID until this release next opens the catalog: every open gives each photo without one its own, and reads report it missing until then. So every photo of a catalog gets its UUID the first time this release opens it, after any format upgrade; a copy made before that (the upgrade's own backup, a Time Machine copy, a copy for a laptop) gets different UUIDs of its own when it opens. The same holds for a photo an older release added while this one had the catalog open: an Export as Catalog made before the next open gives it a UUID of the export's own.

Two things releases before it refuse on a catalog this release has opened, as they refuse any table a later release adds: **Export as Catalog** ("A later release of RAWmakase added to this catalog (photo_uuids)"), and, in 0.6.1 to 0.7.2, removing unused masks and AI Remove patches ([above](#unused-masks-and-patches)); this release still removes them.

## SQLite format, versions 1 to 7

New and imported catalogs are version 7. Version 2 can hold raster masks (content-addressed in the `bitmaps` table, referenced by recipes, History and snapshots; deleted once nothing names them, see [below](#unused-masks-and-patches)). Version 3 holds edits rendered by the one engine: every stored recipe (edits, History steps, snapshots) has lost the settings earlier releases chose a rendering engine or operator with (`model::saved_format::OBSOLETE_SETTINGS`); slider values and settings this release does not know are kept. Version 4 may hold Lensfun lens choices ([lens corrections](lens-corrections.md#lensfun-profiles)), version 5 AI Denoise settings ([AI Denoise](rendering-quality.md#ai-denoise)) and version 6 HDR edits ([the HDR plan](records/hdr-implementation-plan.md)), each of which the releases before it would have rendered or saved without. Version 7 stores each camera profile and Lensfun calibration an edit uses once, in the `recipe_assets` table (named by content: `sha256:` of the value, zlib-compressed), and every stored recipe, History state and snapshot names them by that id (`"profile": "sha256:…"`, and `"calibration"` in a Lensfun choice) instead of holding its own copy. An edit still renders bit for bit after its profile file is removed or updated, or on another computer: the catalog holds the profile, as it held the copy before. A profile fitted to one photo (Camera Look) is that photo's own, so a catalog of many fitted looks stores many. An edit whose profile is a look also names, under `"look_source"`, the look's settings as Lightroom writes them (stored the same way, kind `look_source`), which RAWmakase needs only to write the look into presets and exported files ([Writing looks out](lightroom-profiles.md#writing-looks-out)); releases that predate them keep the reference as an unknown setting. Stored profiles and calibrations are never deleted; Export as Catalog leaves out the ones its copy no longer names, keeping all of them when a History can't be read. Version 7 also drops `preset_settings`, a copy of an applied XMP preset's settings that recipes carried and nothing read. Version 7 is also the first that may hold generated spots (an edit, a History state or a snapshot with a Generate spot and its patch; see [AI Retouch](retouching.md#ai-remove-and-ai-replace-experimental)), which releases before it can't render and would drop when saving; the patches' pixels are in the `bitmaps` table, as mask rasters are. Builds between catalog format 7 and generated spots can't read such a recipe (its spot's mode and patch are unknown to them): one in an edit or its History protects that edit, and one in a snapshot leaves the snapshot out of the list; either way its rows stay as stored. Releases before each version refuse it, the file left unchanged.

A catalog of an earlier version is upgraded when it opens, an empty one included. A verified SQLite copy of it is written beside it first (`<name>.before-upgrade-backup`, then `-1`, `-2`…, as large as the catalog; it is a recovery copy, not a second catalog, and opens in the release that used the catalog before). Only the newest backup is kept: the next time the Library or the command line opens the catalog after an upgrade, the backups earlier upgrades left beside it are deleted (the upgrade says how many). The one kept is the one the last upgrade wrote, recorded by name in `meta` (`upgrade_backup`); for upgrades of releases before this, which recorded none, it is the one of the newest format. A backup is never deleted in the session that wrote it; only files named exactly as upgrades name them that are RAWmakase catalogs are deleted, so a renamed one is left alone. Then one immediate transaction gives it the tables added since, rewrites every stored edit, History and snapshot a batch at a time (only the profile, the calibration and the obsolete settings change; settings and History fields of later releases stay as they were written, to the byte), stores each profile and calibration once, reads every rewritten row back through that transaction (never from what the process holds) to check it gives the same recipe, and raises the version. A row this release cannot read (damaged, or a History of a newer release) is left as it was and counted. Then `VACUUM` gives the disk the space back; when it fails, opening goes on and says so. Opening shows the progress ("Upgrading catalog: 1,240 / 30,000 edits"; the command line prints it), cannot be cancelled (quitting rolls the transaction back), and afterwards says where the backup is. When the backup or the upgrade fails (a full disk, say: the error says how much space the backup needs), the catalog is not opened and its file is left unchanged; free space and open it again, or open the backup in the older release. Close the catalog on every other computer first; mixed-version concurrent use is not safe. Every edited photo's Library previews are made again once after the upgrade, as what identifies an edit now names its profile by content. Export as Catalog copies the catalog's version, 7.

A `.rawmakase` file is SQLite with application ID `0x4f4d4152` and `PRAGMA user_version` 1 to 7. Core tables: `sources`, `roots`, `folders`, `photos`, `collections`, `collection_photos` (and `collection_options`, `smart_collection_rules` and `keyword_synonyms`, above), `keywords`, `photo_keywords`, `folder_mappings`. `import_batches` and `photo_imports` record which Add Photo Folder, Synchronize or Import Photos (`kind` `add`, `sync` or `copy`) added each photo (Previous Import is the newest batch). `photo_checksums` keeps each master's file checksum (size, quick and full SHA-256, the `Identity` of the version read and the hashing version); it is new without a format change, so older releases ignore it, and its rows go with their photo. `photo_import_facts` keeps what each master was when it entered the catalog: its file's name then, its size and the capture time its file's EXIF gives, the last read in the background (`exif_read` 0 until then) apart from `photos.captured`, which XMP and the user may set; it feeds the Original filename token and Import Photos' suspected duplicates. Photos added before it have no row, and none is made up for them. `photo_uuids` keeps each photo's own UUID ([above](#photo-uuids)). `editable_previews` records each master photo's editable preview ([editable previews](editable-previews.md)): the original's `Identity` it was built from (the only place it is kept), the file's name in the catalog's copies folder (`<catalog name>.rawmakase-editable-previews/` beside it, `<photo id>-<identity key>.dng`, made from that identity when the row is recorded), its format (`rawmakase-dng-1`), whether it is out of date and when it was built. Virtual copies share their master's row and Set Copy as Master moves it; a row an older release's promotion leaves on what is then a virtual copy is not looked for, so the family has no copy until one is built again. It is new without a format change, older releases ignore it, and its rows go with their photo through `ON DELETE CASCADE`, whichever release removes the photo; a copy no row names any more is listed for deletion. Export as Catalog carries the rows and files of the photos it exports. `catalog_counters` holds numbers the catalog hands out once (`import_number`, Import Photos' Import #; `keyword_id`, the highest keyword id given, so a deleted keyword's id is never given again and Undo puts back the right keyword; `keyword_applied`, the last number `keyword_applied` took). `keyword_applied` records when each keyword was last given to a photo, for Recent Keywords, as Lightroom's `lastApplied`; it is new without a format change, and older releases ignore it. Both are new without a format change, and older releases ignore them; a photo added by an older release simply has no facts row. A photo's id is never given to another photo, as in Lightroom, so a request naming a photo that is gone (an extension's proposal, MCP's `photo_ids`) can't land on a new one: each new photo, whether imported, a virtual copy or added by Add Folder, takes an id above both the highest in `photos` and `photo_id_high` in `meta`, and removing a photo raises that mark to the highest id first; a Lightroom import keeps Lightroom's ids and sets the mark to the highest. The mark is new without a format change. A catalog without it starts from its highest photo: ids removed before this release can't be known, and an earlier one may already have been given again. Releases before it ignore the mark and may still give a removed photo's id out again; they can't lower it, as each new photo here takes the larger of the mark and the highest id. Export as Catalog copies `meta`, so the exported catalog never gives out an id its source had given before the export. The statements are portable: on Postgres, whose identity columns never reuse an id anyway, they give the ids the same way, as collections' are given. Per-computer folder locations live in `computers`, `folder_paths` (each folder's logical path, names joined by `/`) and `folder_locations`; `roots.mapped_path` and `folder_mappings` are kept for older releases. `file_operations` and `file_operation_members` are the journal of file operations (moving and renaming photos' files, renaming and moving folders, putting files in the Trash, with where the Trash put each): each item and each file it touches, written before every step, so an operation a crash cut short is finished, put back or reported by recovery, never guessed; photos moved or renamed within a drive are journalled up to 100 items in one commit, and each step of theirs (every item's photo, then every item's next file) is synced once per folder and journalled in one commit, so each item's files still go one after another, each synced and journalled before its next (#692); recovery runs before every file operation and when the Library opens the catalog. Making a folder is journalled too: its path before it is made, its file object and the name the disk gave it after, so a folder whose making wasn't recorded is never added to the catalog for it. `file_operation_copies` is what a move to another drive copies, a row for each file: its hidden partial copy's path, journalled before it is made, the copy's file object once it is, the SHA-256 it was verified with, its `Identity` once the catalog follows it, where the Trash put the copy when the move was undone, and why an original stayed; such an item is `committed` once the catalog follows its copies and `done` once its originals are dealt with. A folder moved to another drive is one such item: its members are the folder, the folders in it, then its files, each with a row there (its place inside the hidden folder as `temp`), and its journalled state says how many of them are folders. Apart from a photo the user deletes permanently (below), a partial copy is the one file RAWmakase ever deletes outright, by its journalled file object or, made but not yet journalled, at the name the journal gave it and only while empty, and never on an SMB share; a whole copy goes only to the Trash. They (and `file_operation_copies`) are new without a format change, so older releases ignore them (an unfinished item's checks are made again first, so a change an older release made meanwhile is reported, not acted on); finished items are forgotten after 30 days. While files are being changed (not for Remove from Catalog, which changes none), RAWmakase holds an OS lock on `<catalog>.file-operations-lock` beside the catalog (named after its real path, through any link), so a second window can't change the same files; the file is left in place. A rename keeps each file's extension and renames the sidecars only it reads to match, refuses the whole rename when any name is taken, given twice or another photo's in the same rename, and renames a folder, or moves it into another folder of its root on the same drive, only when nothing below it is located on its own, re-keying `folder_paths` and the legacy `folders.relative_path` of its subtree. Remove from Catalog is journalled too. A folder put in the Trash is a `trash_folder` item: its state is the subtree's catalog folders and photos, each family's digests and how its names are proven, and its members are every name of the tree (the folder, its folders, then its files), each `trashed` with where the Trash put it. It is new without a format change, but a release before it (0.4.2 and earlier) can't read the kind and fails closed on an unfinished one rather than act on it: on the computer that made it, its recovery fails and so does every file operation that takes the lock; on any computer, Remove from Catalog and planning a folder rename or move fail with that error; until this release decides the item or the user keeps it. A finished one is never read by those releases. An Import Photos run is `import_copy` items (one per photo or family of photos sharing a sidecar, and a finish item), whose state journals what the run was asked for, Apply During Import included, so recovery adds a photo as the run would have. A release before Import Photos can't read the kind and fails closed on an unfinished one, as on `trash_folder`: its recovery and every file operation that takes the lock fail until this release finishes or keeps the item. Its Add Folder isn't held back from such an item's copies; should it add one, this release's commit finds the photo there and leaves the item to Keep as Is, losing nothing. A root folder moved into another root is a `move_root` item (#586), a folder item like `move_folder` whose state moves the root's own logical path (`""`), so a release before it (0.4.6 and earlier) fails closed on an unfinished one the same way rather than take it for a folder move within a root; this release reads `move_root` only with that path and `move_folder` and `rename_folder` only without it. Deleting photos permanently (#1273) is a `delete_photos` item, journalled as Move to Trash's photo items are, each member `deleted` once its file is; a release before it can't read the kind or the state and fails closed on an unfinished one the same way. The transaction that re-keys the root's folders into the other root also removes the root and its locations on every computer. Foreign keys are enabled. Photo recipes and export options are JSON fields, separate from `lightroom_develop`. Saved recipes include source identity checks, so a replaced file cannot silently overwrite a previous edit. Unknown future catalog versions are refused.

Creation/import publish atomically without clobbering another file. SQLite transactions protect metadata and recipe writes. Back up the `.rawmakase` file with RAWmakase closed. No Lightroom file or RAW is modified by catalog operations.

## CLI

```sh
rawmakase import-catalog input.lrcat Photos.rawmakase
rawmakase catalog-info Photos.rawmakase
rawmakase relink-catalog Photos.rawmakase ROOT_ID /local/photos
rawmakase Photos.rawmakase
```

`catalog-info` lists source root IDs and their locations on this computer; `relink-catalog` changes a root's location on this computer only. Synthetic tests exercise exact source preservation, removing an archived `.lrcat`, virtual-copy isolation, metadata, collections, keywords, descendant relinking, idempotent folder imports, changed-source protection, malformed/active catalog rejection, rollback and no-overwrite behavior.

## Decoded-image cache

Preferences > Catalog > **Decoded images > Cache size limit** sets how much disk space
to keep for decoded RAWs, from 1 GiB to 1 PiB (1,048,576 GiB; 4 GiB by default). This cache is
shared by all catalogs and avoids repeating RAW decoding and highlight recovery
when reopening a photo; the current edit still needs rendering. Develop, neighbour
preloading and Reference View share the limit. Changes are saved between launches
and apply without restarting; lowering the limit removes least recently used
entries on the next cache write. Rendered Standard and 1:1 previews have separate
budgets. See [the decode cache](preview-performance.md) for its location and identity.

## Preview cache

Library thumbnails are generated on demand and stored as JPEG blobs in a separate `~/.local/share/rawmakase/previews.sqlite3` database (`$XDG_DATA_HOME/rawmakase`, or `RAWMAKASE_DATA_DIR` when configured). All catalogs share this disposable cache. A thumbnail from an older preview generation is made again when next shown: JPEG, PNG and TIFF thumbnails made before their ICC profile was honoured are replaced, while RAW thumbnails are kept. Catalog databases continue to hold metadata and edits only.

The cache checks file size, nanosecond modification time and the preview generation before reuse. A RAW's own thumbnail is its embedded preview (the camera's JPEG, or the JPEG XL Lightroom writes into a DNG), not an engine render, so it is kept across engine changes and made again only when extracting embedded previews changes. A RAW without an embedded preview the Library can show (none, or only uncompressed ones, as a film scanner's DNG has) and without an edit is developed with the defaults instead, as Develop would open it, and kept as an edited thumbnail, made again once profiles are imported or removed (the defaults may pick another); edited thumbnails, and those of JPEG, PNG and TIFF files, are made again whenever the engine renders differently. A file keeps the edited thumbnails of its eight edits used most recently, each with all its variants (with and without AI Denoise's result), so saving edit after edit doesn't fill the cache with renders of edits that were replaced. Previously generated previews remain usable while originals are offline. Missing Lightroom preview bundles cannot be reconstructed from the `.lrcat` alone; a photo needs to be available at least once to generate its preview.

SQLite WAL permits concurrent readers/workers. The thumbnails' image-payload budget is 512 MiB by default, about 6,000 thumbnails (Preferences › Performance › Thumbnail cache offers up to 16 GiB, for a large catalog on a network drive, where a thumbnail made again means reading its photo again; choosing less prunes at once and gives the space back to the disk in small steps, off the UI thread), with least-recently-used eviction, thumbnails no lookup can show any more (made by an earlier engine) going first; an additional 192 thumbnails, or as many as the views show at once, are retained in GPU memory, the oldest not shown dropped first. Corrupt individual images are discarded and regenerated. Cache failure falls back to uncached previews. With RAWmakase closed, the preview database and its WAL/SHM companions can be deleted without losing edits. This cache currently covers original Library thumbnails, not full-resolution Develop renders.

The same file has room for larger previews built on request (issue #213): Standard previews, sized for Develop to show while a photo opens, and 1:1 previews at full resolution. They are keyed by file, by an identity of the edit they show and by kind, so virtual copies and edits each get their own row, and they follow the thumbnails' offline and staleness rules. Each kind has its own least-recently-used budget (Standard 2 GiB, 1:1 4 GiB), so building one never evicts thumbnails or the other kind. A row records the edge it was built for apart from the size it reached, so a small original or a tight crop is not rebuilt each time. Which catalog photos had previews requested is kept in its own table, per catalog and photo, so a virtual copy or the same file in another catalog never inherits them; discarding a photo's previews or removing it from the catalog forgets the request. These tables were added without changing the cache's format version, so older builds keep opening the file. The space discarded, cleared or expired previews leave in the file is given back to the disk in the background between builds, in writes of about 25 ms at most with a pause after each, so the file shrinks without holding up the thumbnails; what is left at quitting, or after a failed write, is given back by the next discard, clear or automatic discard (run at launch), and a little after each prune.

**Build Standard-Sized Previews**, in a thumbnail's menu under Previews (in the Library grid and the Develop filmstrip), builds them for the selection, or the photo clicked when it is not selected. Offline photos and files Develop can't open are skipped and counted, and photos whose preview is still fresh cost nothing. Each photo is rendered as an export would render it, from its edit as the catalog has it then (the open photo's is saved first): a protected or unreadable edit fails that photo with its reason and never falls back to the defaults, and Upright is worked out first. The half-size decode is used when it is large enough once cropped and transformed, else the full one. Builds run one at a time in the background, never blocking navigation; the top bar shows "Building previews 12 / 150" with a button that stops them, then what could not be built. A photo shown edited in the grid takes the build as its thumbnail too, unless Develop rendered it, or its edit changed, since. **Discard Standard and 1:1 Previews** removes the files' built previews and the photos' requests. Preferences > Catalog sets the **Standard Preview Size** (1440, 2048 or 2560 pixels, 2048 by default), shows what thumbnails and each kind of preview take, and clears Standard previews. Automation's `build_previews` does what the menu does for the selection.

While a photo opens in Develop or the Loupe, its Standard preview for its current edit, when there is one, is shown at once, in place of the camera's embedded JPEG, until the first live render replaces it; the next photo's is read ahead. It is only a picture: the readout, white balance picking, the histogram, tools and Before/After wait for the photo itself. An offline RAW, or an edited JPEG, PNG or TIFF, in the Loupe shows its Standard preview instead of the grid's thumbnail. **Build Standard-Sized Previews** skips a JPEG, PNG or TIFF without an edit: its file is its preview. When a photo whose previews were built is saved with another edit (on leaving it, by Sync or Paste Settings, or an Undo of those), its Standard preview is built again; a virtual copy, or the same file in another catalog, has its own requests and is not rebuilt with it. Measurements are in [preview performance](preview-performance.md#stored-standard-previews--2026-10-08).

**Build Editable Previews**, in the same menu, builds for each selected RAW a copy that Develop edits it from while its original is offline ([editable previews](editable-previews.md)): 2560 pixels on its long edge, in the catalog's copies folder, one per master photo, which its virtual copies share. Offline photos and other files are skipped and counted, and a photo whose copy is of its original as it is costs nothing. Builds run one at a time in the background at a fixed pace; the top bar shows "Building editable previews 3 / 12" with a button that stops them, then what could not be built. The grid marks a photo with a copy with a small square in its footer, struck through once the copy is out of date (its original came back as another file), and the Metadata panel says which. An offline photo with an up-to-date copy opens in Develop, labelled Editable Preview; its edits are saved as the original's and render from it once it is back. AI masks, AI Denoise and Fit Camera Look need the original, as do Export, Sync and presets from the Library. **Discard Editable Previews** forgets the selection's copies and deletes their files, stopping a build of them under way. Build and Discard also delete the files no copy names any more (left by a photo removed from the catalog, say).

**Build 1:1 Previews**, in the same menu and through `build_previews` with `kind: one_to_one`, keeps each photo at full size, rendered from the full decode. Their one use is an offline RAW in the Loupe: a click zooms it to 100% from its 1:1 preview, where without one zooming needs the original. Online photos zoom from the photo itself, which once decoded presents a 100% region in well under 0.1 s, so a 1:1 preview would not make that faster ([measurements](records/preview-performance-measurements.md#11-previews--2026-10-08)). A 1:1 preview is large (a 61 MP photo's is tens of megabytes), so they are kept in the cache with their own 4 GiB budget, and Preferences > Catalog discards those unused for a day, a week or 30 days (the default), or never, as Lightroom's Automatically Discard 1:1 Previews does; **Discard 1:1 Previews** and **Clear 1:1 Previews** remove them at once. A photo larger than a JPEG can hold (65,535 pixels a side) is reported and not kept.

The folder tree uses expandable nested rows and aligned counts. Selecting a folder includes its descendant folders. Shift-click selects the folders shown between the folder last clicked and this one, and ⌘-click (Ctrl-click on Windows and Linux) adds or removes one, so the grid shows several folders' photos together; the last folder can't be removed this way. The source name reads "3 folders", Synchronize Folder in the Catalog menu needs a single folder (right-click a folder to synchronize it), and on the next launch the Library returns to the folder the selection started from. Library and Develop are available through the workspace tabs or G/D shortcuts.

On Linux, desktop network shares require the GVFS FUSE bridge for native filesystem access. RAWmakase starts the installed `gvfsd-fuse` helper when needed before catalog loading or directory selection. Existing GVFS mounts and desktop-managed authentication are reused; no credentials are stored by RAWmakase.
