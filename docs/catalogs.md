# RAWmakase catalogs and Lightroom import

Dropping a folder onto the window adds it and selects that folder (including its
subfolders) in the Library. Dropping several folders selects their combined scope;
unrelated catalog photos stay out of the view. The filter bar clears for the
imported folders so existing filters do not hide the newly added photos.

A folder chosen in the Folders panel shows the photos in it and in its
subfolders, and its count says how many. **Show Photos in Subfolders** in a
folder's right-click menu turns that off, as in Lightroom's Library menu: each
folder then shows and counts only the photos directly in it (a folder holding
only folders shows none), until it is turned on again. The choice is kept with
the Library's layout across launches. Remove from Catalog, Synchronize Folder
and the drives' counts still cover a folder's subfolders.

Use **Catalog → Import Lightroom catalog…**, select a closed `.lrcat`, then choose a new `.rawmakase` filename. Existing destination files are never overwritten. **New catalog** creates an empty library; **Add photo folder** recursively registers RAW files (any extension in `RAW_EXTENSIONS`), JPEG, PNG, TIFF, WebP, AVIF, HEIF (`.heic`, `.heif`, `.hif`) and JPEG XL files without copying or modifying them. The last four are read only: they are catalogued, shown and edited, but export to them is not available yet.

**Library** (`G`) provides a virtualized thumbnail grid, folder browsing, filename/keyword/date/label search, minimum-rating and flag filters, offline filtering, capture-date sorting, and rating/flag/color-label editing. Double-click an available photo, a RAW file (see `RAW_EXTENSIONS` in `src/storage/files.rs`) or a JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL, or select it and use **Develop** (`D`); an offline photo is refused, as is a rendered file whose header says Develop can't edit its pixels (a CMYK JPEG, an HDR or animated WebP, AVIF, HEIF or JPEG XL, or a tiled AVIF, say; "RAWmakase can't edit HDR images"), with the reason in a dialog and under Quick Develop. A JPEG, PNG, TIFF, WebP, AVIF, HEIF or JPEG XL is edited from its own pixels with the Embedded profile and relative white balance, as Lightroom does ([rendered files](color-pipeline.md#rendered-files-jpeg-png-tiff-webp-avif-jpeg-xl)). Until it has an edit, the Library and Loupe show it as its file, converted from its embedded ICC profile to sRGB (a file without one is taken as sRGB), which its defaults reproduce; once edited, it is shown developed, as a RAW is. An HDR or animated file still shows in the Library, as a plain preview of its first frame (an HDR one tone mapped for an SDR screen); a tiled AVIF and a 4:2:2 or monochrome HEIF show nothing. Library thumbnails are original embedded/file previews, not Lightroom-rendered previews.

**Develop** retains the preset browser and editing controls. When the photo belongs to a catalog, edits and export options save in that catalog rather than beside the photograph. Virtual copies share the source photograph but have independent recipes. Create Virtual Copy (⌘' or the thumbnail menu, in Library and Develop) starts a copy from the photo's current edit, rating, flag, label and keywords, named Copy 1, Copy 2 and so on. The thumbnail menu also offers Set Copy as Master and Remove Virtual Copy (which asks first and leaves the file alone); rename a copy in the Library Metadata panel's Copy Name field. Copies show a folded corner on their thumbnail and their own edited preview. Opening a RAW file directly goes through the Library: a photo already in the open catalog develops from it, and an unregistered photo has its folder added to the catalog first, so its edits save in the catalog too. Edits saved beside the file by releases before 0.1.8 are imported when that folder is added, and the sidecar is left on disk. Opening a catalog photo does not implicitly import a possibly unrelated RAWmakase sidecar.

**Stacks** group photos of one folder under one of them, the top, as Lightroom's folder stacks do. Select photos and press ⌘G (or Stacking › Group into Stack in the thumbnail menu): the active photo becomes the top and the stack is collapsed, showing the top alone with a badge counting its photos. Click the badge or press S to expand or collapse it; expanded, its photos sit together in stack order, each marked "2 of 3" and so on, wherever the top sorts. Shift+S makes the active photo the top; the menu also moves a photo up or down, takes photos out of their stack (Remove from Stack) and collapses or expands every stack. ⌘⇧G unstacks. A collapsed stack's top stands for the whole stack to Group into Stack and Unstack; ratings, flags, labels, keywords, Quick Develop, Sync and export apply to the photos selected, so to the top alone, as in Lightroom. A filter shows every photo it matches: when it hides a collapsed stack's top, the stack's first photo that matches shows in its place. All Photographs and folders show stacks; collections and Previous Import list their photos one by one. **Auto-Stack by Capture Time…** (the thumbnail menu's Stacking, or Photo › Stacking in the macOS menu bar, as in Lightroom) stacks photos of each folder shown that are in no stack yet, joining each photo to the one before when it was taken less than Time Between Stacks later (up to an hour; none at 0:00:00), and shows how many stacks it would make before it does. With **Group camera bursts** ticked, it reads what each camera wrote in its maker note: a burst or bracket becomes one stack, first frame on top, however long it took, and two bursts shot within Time Between Stacks of each other stay apart. Sony (SequenceNumber, 0xb04a), Fujifilm (0x1101) and Panasonic (0x002b, read from an RW2's JpgFromRaw) number each press's frames from 1, so a run of rising frame numbers from one body and in one format is one burst, each frame at most a minute after the one before; culled frames leave a burst whole, but a burst whose first frames were deleted joins the one before it if shot within that minute. Two bodies of one model tell apart only by the EXIF's body serial number. Photos taken in the same second follow their file names. An iPhone gives a burst's photos one BurstUUID. Olympus and OM System bodies number some sequences' frames too (DriveMode's shot number). Canon (ContinuousDrive and BracketMode; its own counter is 0 in most files) and Nikon (ShootingMode) say only whether a photo was shot in continuous drive or a bracket: those photos stack by capture time as Auto-Stack does, each body's and format's apart, so two presses less than Time Between Stacks apart make one stack, and a single shot or a numbered frame of the same body ends the run. A DNG Adobe converted is read from the camera's note it keeps (DNGPrivateData's MakN block, even when Camera Raw copied it from 12 bytes too early; for a Panasonic, the JpgFromRaw in its Pano block), a CR3 from its CMT3 box. A photo the camera says was a single shot is left alone; photos of other cameras (older Sony bodies such as DSLR-A, NEX and SLT, Pentax, Leica…) and unreadable files stack by time, never across a photo whose camera said something. Virtual copies are left alone. What the maker notes say is kept in the catalog (`photo_sequences`) with each file's size and modification time, so a file is read once and again only when it changes: a photo added from a folder has it read in the background with its photo info. When the box is first ticked, the window checks each candidate's file (one stat), takes what the catalog kept of a file that is unchanged, and reads and saves the rest (photos imported from Lightroom, those added before this release, files replaced since); an offline file stacks by time and nothing is saved of it. Stack waits for them, and stays off if the read stops before every photo (untick and tick the box to read again). A release that reads more cameras' notes reads every file again once. Releases before it ignore the table. **Stack camera bursts** in Preferences › Catalog › Adding photos (off by default) does the same for photos added from folders and by Synchronize Folder, without being asked: once their files are read in the background, each burst or bracket becomes a collapsed stack as Group camera bursts makes it, frames a camera didn't number (Canon's, Nikon's continuous drive) joining while less than two seconds apart; photos whose camera says nothing, or that are in a stack by then, are left alone, and nothing is stacked by time. The choice is taken when adding starts and kept with the batch in the catalog (`import_burst_stacks`) in the transaction that adds its photos, so the stacking survives a restart or another catalog being opened meanwhile; it is done in the Library, with nothing open over it (it waits while Auto-Stack's window is open, a file operation or Synchronize holds the catalog, or the window shows Develop), as one step for Undo, after which the batch is done and Undo leaves it unstacked. A batch with a photo offline waits until it is back; one whose read stopped is read again when the catalog opens or its files' availability changes. Export as Catalog leaves the batches still to be stacked behind, and a release before this one refuses to export a catalog with the new table, as it does any table it doesn't know. Each change, Auto-Stack's included, is one step for Undo; collapsing and expanding are kept with the catalog and aren't. A new virtual copy goes right after its photo in its stack (or makes a stack of the two), expanded so it shows. A photo moved to another folder leaves its stack; renaming photos or a folder, or moving a whole folder, keeps them. Removing a photo takes it out, and a stack left with one photo is no stack. Stacks are kept in the catalog only, never in XMP; importing a Lightroom catalog brings its folder stacks, with their tops and whether they are collapsed. Lightroom's collection stacks aren't imported. Releases before stacks open a catalog with stacks and leave them be; what they remove or move is read correctly afterwards.

**Delete** or Backspace in the grid, the Loupe or the filmstrip (in Develop, while no tool is open) asks, as Lightroom does, whether to **Move to Trash** or just **Remove from Catalog**; photos whose files are missing or offline are only offered Remove from Catalog. **Remove from Catalog** takes photos out of the catalog and leaves their files where they are: press ⌥Delete, or choose Remove from Catalog… in the thumbnail menu, to ask for it alone. It acts on the selection, or in the Loupe on the photo shown. A master takes its virtual copies with it; copies chosen without their master go alone. RAWmakase asks first, and says how many photos and copies go and how many have edits made in RAWmakase. Those edits, with the photos' ratings, keywords and History, go with them: adding the file again doesn't bring them back. In that question Cancel has the focus, so Return, Space or Escape alone cancel; Remove from Catalog needs a click, or Tab to it first. A key still held when the question appeared (Delete repeating) does nothing until it is released. The open edit is saved before anything is asked, and if it can't be saved nothing is removed. While photos are being removed the top bar says so, with Stop, which ends it after the photo under way. Delete in the Quick Collection only takes the selected photos out of it, as one step Undo brings back; in an imported Lightroom collection, which can't be changed, it does nothing and the status line says so.

**Move to Trash** puts photos' files in the system Trash (the Recycle Bin on Windows, the freedesktop Trash on Linux), with the XMP sidecars and earlier releases' edit files only they read, then takes the photos, their virtual copies included, out of the catalog. Choose it in Delete's question, press ⌘⌥⇧Delete, or choose Move to Trash… in the thumbnail menu. The question says how many files and sidecars go, and that edits made in RAWmakase go with the photos: putting a file back from the Trash brings back the file, not its edits. Nothing is ever deleted outright: a file goes to the Trash or stays, and the catalog lets a photo go only once the Trash has its file and it is gone from its folder. A volume with no Trash (some network drives and disk images) keeps the file and the photo, and the top bar says to delete it in Finder if you're sure. **Delete Rejected Photos…** (⌘Delete, or the Catalog menu) asks the same as Delete for the rejected photos of the folders or collection shown, whatever is selected or filtered.

**Moving photos to another folder** moves their files on disk, and the catalog follows. Drag the selected photos from the grid onto a folder in the Folders panel, or choose **Move to Folder…** in the thumbnail menu and pick a catalog folder. **New Folder Inside…** in a folder's menu makes a folder there, on disk and in the catalog, and offers to move the selected photos into it (ticked when they are all in that folder). A master's virtual copies go with it, and so do the XMP sidecars and earlier releases' edit files only it reads; one another file reads too stays where it is. RAWmakase asks first, saying how many files and sidecars move and which photos stay and why, with Cancel focused as for Remove from Catalog; a folder made with nothing moving into it is made on Create. The destination may also be a folder of a root that has no photos of its own yet (one holding only folders, or a root folder with photos only below it): its directory must be there, and its folder joins the catalog in the same step the photos' rows follow, never before. Within a drive files move by renaming them, so their bytes and dates don't change and their edits and checksums stay valid; nothing is ever replaced: a name taken in the destination (on disk, or by a photo of the catalog, even an offline one) leaves that photo where it is. To another drive (an external disk) each file is copied instead: into a hidden `.<name>.<run>-<item>-<file>.rawmakase-part` file there (which Synchronize Folder and Add Photo Folder pass by), read back and compared with what was read of the original (SHA-256), given the original's extras (its Finder tags and other extended attributes, FinderInfo and resource fork on macOS; its `user.` extended attributes on Linux; its alternate data streams, such as `Zone.Identifier`, on Windows), read back and compared too, its date and permissions, then given its name, never replacing one there. A drive that can't keep an original's extras (FAT and exFAT on Linux and Windows; macOS keeps them there in `._name` files) leaves that photo where it is, and says so; what the system keeps for itself (macOS's `com.apple.provenance`, Linux's `security.` labels and access lists) isn't carried. The catalog follows a photo only once every file of it is copied and its original is still the file that was copied; only then do the originals go to the Trash. A move whose copies wouldn't fit on that drive (with 32 MB to spare) is refused before anything is copied, and so is a move to or from a network drive other than an SMB share (on a Mac, mounted as CIFS on Linux, or a network drive or `\\server\share` folder on Windows), or any other whose files RAWmakase can't tell apart (copy them in Finder, then use Synchronize Folder); a move within such a drive renames as on any other. Local APFS and HFS+ (macOS), ext2/3/4, XFS and Btrfs (Linux) and NTFS (Windows) drives keep the numbers that tell a copy from another file of its name. FAT and exFAT drives (SD cards, most external SSDs) number their files anew as they are written, renamed or plugged in again, so there a copy is told by its exact name and its bytes instead (SHA-256 of what was copied), and an original by its name, its size, date and first bytes, and, before it goes to the Trash, all its bytes again; no such number is recorded for a copy there (one no file has stands in, so an earlier release leaves such a move for you rather than act on it). An empty file found where a copy was being made, before that was recorded, is taken for the copy only when the drive says it was made after the move was planned. exFAT on macOS can't give a name only where none is, so there each copy is made at its name straight away (never replacing a file), and one a move undoes goes to the Trash. An SMB share (a NAS, or a Windows or Mac computer's shared folder), on a Mac, mounted as CIFS on Linux (`mount.cifs`), or on Windows (by drive letter or `\\server\share` path), is moved to and from as macOS's exFAT is: each copy is proven by its name and bytes and made at its name, as a share can't promise that a rename won't replace a file another computer put there. A copy a move onto a share undoes would go to the Trash, which a share hasn't got, so it stays there, even part-made or empty: nothing on a share can be removed only while it is still the copy RAWmakase checked, and another computer could put its own file at that name just then. The move is listed under **Unfinished file operations**, saying its copies were left on the share; delete them there (Put Back changes nothing while they are there), and it clears, or choose Keep as Is. It says so only while every original still holds all of its copy's bytes, and every folder a folder move left there holds nothing but its copies: a copy whose original changed meanwhile may be the only one of those bytes left, and a file another computer put in such a folder isn't RAWmakase's to have you delete, so such a move is listed as not put back instead. A Mac has no Trash on a share, and Linux's (the share's `.Trash-$uid` folder) and Windows' (a folder redirected to a share has a Recycle Bin there) are filled by a rename that can replace a file another computer put at its name, so they aren't used: photos moved off a share are copied and checked, and their originals stay where they were (nothing is deleted instead): the question says so before anything is copied, and the outcome lists them, to delete in Finder once you've checked the copies. For the same reason nothing is renamed on a share: renaming photos or folders there, or moving them within one share, leaves them as they were. A share drops an extended attribute with no value, so a file or folder with one stays where it is; on Windows, a share whose server keeps no alternate data streams (Samba without `streams_xattr`) keeps none, so a file with one (`Zone.Identifier`, say) stays where it is, and its copy there is left for you to delete. A share's listing can lag what another computer did, so a file there (as on FAT and exFAT) is taken for gone only when its folder lists no such name and looking it up finds nothing. NFS, WebDAV and FUSE shares stay refused; so do GVFS's on Linux (a desktop's `smb://` places), which keep no birth times, permissions or extended attributes and number files anew each mount: mount such a share with `mount.cifs` to move files on it. The hidden partial copy is found by its name however the drive spells it (HFS+ keeps names decomposed). A partial copy written whole is kept, never removed, while its original can't be found as it was, and a name there held by another file is never taken for the copy gone: such a move is listed for you. A drive that keeps dates more coarsely (exFAT, FAT, HFS+, NTFS) gives the copy the nearest date it can; the photo's edit and checksum then move to the copy, which has the same bytes, unless the photo still has an edit file from a release before the catalog beside it, which names the original's date: that photo stays where it is. An original the Trash can't take (a drive without one), that changed since it was copied, or whose extras aren't its copy's any more (tagged meanwhile, say) stays where it was, beside its copy, which the catalog follows, and the outcome says which and why. A copy that fails (a full drive, a file that reads back differently or changed while it was read, a name taken there meanwhile, Stop, which stops a copy between 1 MiB chunks) is undone: its partial copies are removed, its complete copies go to the Trash, and the originals and the catalog are as they were. A folder's name is refused when Windows or macOS couldn't use it, and one already there, or that the catalog has (even missing), is never taken for the new one. While photos move, the top bar counts them, with Stop. The open photo follows its file, and its edit saves there. When a catalog opens, RAWmakase finishes what a crash cut short where the files prove where they are: a move to another drive the catalog already followed has its originals put in the Trash, each only while it is still the file copied and its copy reads back the same, and one it didn't follow is undone once every original is proven where it was; what it can't decide is listed under **Unfinished file operations**, each with its files and why, to **Put Back** (renamed back where they were; for a move to another drive, its copies put in the Trash (a partial copy not yet whole is removed) while each original is where it was, even if it changed since; while one isn't, it says so and changes nothing), **Keep as Is** (Synchronize Folder can match the files later) or, for a folder made, **Add to Catalog** when it is proven the folder RAWmakase made. A folder is never deleted to put one back. **Decide Later** asks again when the catalog next opens.

**Renaming.** Press F2, or choose Rename… in the thumbnail menu. For one photo, **Rename Photo** asks its new name; the extension stays as it is. For several, **Rename Photos** names them by a Lightroom template (Custom Name - Sequence and the others export offers), with a start number and how many digits the sequence has (`Trip-001`), numbered in the order they were taken: by the capture time the catalog has (for photos added from folders, read from their files in the background after they are added; renaming reads no file for it); photos taken at one time keep the Library's order, and those without a capture time come last, by name. The order is read once when the dialog opens. As you type, the names are checked in the background, so typing never waits for them, and each photo's new name is shown with anything that stops it: a name taken there (on disk, or by a photo of the catalog, even an offline one), given twice, already another photo's in the same rename, or one Windows or macOS couldn't use. Then none is renamed; Rename is the dialog's own, and runs only when every name can be had, once what was typed last is checked. The XMP sidecars and earlier releases' edit files only a photo reads are renamed to match; a file keeps its bytes and dates, so its edit and checksum stay valid, and the open photo follows. A name that changes only in case or accents (`ROUND.NEF` to `round.NEF`) works on APFS (on a case-sensitive APFS volume, a change of case only) and is refused elsewhere for now. **Rename Folder…** in a folder's menu renames it on disk and in the catalog, with its photos and the folders in it (a folder holding only folders, such as `2024-trip` above `day1` and `day2`, too); a root folder is renamed in Finder, then located again, and a folder with a folder inside located on its own isn't renamed yet.

**Moving a folder.** Drag a folder onto another folder in the Folders panel, or choose **Move Folder…** in its menu and pick where it goes (a root folder, or a folder of one: its own root's or another's). RAWmakase asks first, with how many photos move with it, Cancel focused; the folder moves on disk by one rename and the catalog follows: it stays the same folder, with its photos, the folders in it and their edits, and moved into another root folder it becomes that root's. Any folder can be moved, one holding only folders too; a root folder only into another root (below). It isn't moved into itself or a folder in it, nor where a folder or file of that name is (on disk or in the catalog, even missing), nor when a folder in it is located on its own or holds another root folder, nor into a root folder that is offline here.

A root folder can be dragged onto a folder of another root, or onto that root itself, or moved there with **Move Folder…** in its menu, as Lightroom Classic lets a top-level folder be; on the same drive or another, as a folder moves. It becomes a folder of that root, named as its folder is, with its folders, photos, edits and collections, and leaves the list of root folders; the question says so. Where it was located on other computers goes with it, and they find it in that root from then on. It isn't moved into itself or a folder of its own, nor when it holds the catalog, RAWmakase's own folders, another root folder or a folder located on its own (on any computer), nor when it is offline here or the top of a drive, nor where a folder can't go (a name taken, a destination offline, or a drive RAWmakase can't move folders to). Moving a root folder to a new place of its own, with no root to go into, is done in Finder, then **Locate root folder…**.

To another drive a folder is copied whole instead, every file in it (sidecars, hidden files and files the catalog doesn't know too), and the question says how much and that the originals then go to the Trash. It is built inside a hidden `.<name>.<run>-0-0.rawmakase-part` folder there (which Synchronize Folder and Add Photo Folder pass by), each file made where nothing has its name, copied, compared with what was read of its original (SHA-256), given its original's extras, date and permissions as a photo's copy is, and each folder its original's extras (a folder's custom icon is its FinderInfo and an `Icon\r` file with only a resource fork); then that folder gets the folder's name, never replacing anything, and the catalog follows only once every copy is proven and every original is still the file copied. Then each folder there gets its original's dates and permissions (only then, as anything made in it changes its date, and macOS won't rename a read-only folder), and when every original is unchanged, its extras still its copy's, and nothing was added beside them, the folder goes to the Trash whole; otherwise each unchanged file goes on its own, and what stays (the changed or added files, and the folders) is reported. A folder holding a link, a special file, another drive, a file with a second name (a hard link) or two names the other drive would take for one is refused, as is one that wouldn't fit there (with 32 MB to spare), and one to or from a network drive other than an SMB share, as for photos. To and from FAT and exFAT drives, and SMB shares, each copy is proven by its name and bytes as a photo's is, a folder by its name; on macOS's exFAT and on SMB shares, which can't give a name only where none is, the folder is built at its name straight away rather than in a hidden folder; a folder moved off an SMB share stays there once copied, with nothing deleted, as a share has no Trash RAWmakase uses, and the question says so; and a file's AppleDouble file there (`._name`, where macOS keeps what the drive can't) is taken as part of that file; so on macOS a folder holding a file `._name` beside `name` isn't moved onto such a drive, where it would be taken for that file's. Anything stopping the copy before the catalog follows undoes it (on an SMB share, where nothing is removed, what it copied stays and is listed for you, as for photos): still hidden, its copies and folders are removed (a copy written whole only while its original is proven unchanged; otherwise it is left for **Put Back**, which puts it in the Trash); already named, it goes to the Trash whole, and only while it holds exactly what was copied, each file read back, or it is left for the user. A drive that can't keep the extras of a file or folder in it leaves the folder where it is, and says so. **Reveal in Finder** (Show in Explorer on Windows) in a folder's menu shows it in the file manager.

**Moving a folder to the Trash.** **Move to Trash…** in a folder's menu (any folder but a root folder) puts the folder, with everything in it, in the system Trash in one go, then takes its folders and photos (their virtual copies, and copies of photos elsewhere that are in it) out of the catalog. The question counts what goes, folders, photos and other files (sidecars, hidden files and files the catalog doesn't know), names a few of the other files, and says that edits made in RAWmakase go with the photos and that catalog photos and folders in it that are missing on disk leave the catalog too; Cancel has the focus. Right before the Trash the folder is read again and has to hold exactly what was asked about (the same names and kinds, each file the same size, date and first bytes, and where the drive keeps them the same file numbers; on FAT and exFAT by names): anything added, removed or changed since stops it, and nothing moves. Only `.DS_Store`, `Thumbs.db` and `desktop.ini`, which the system writes on its own, don't count; they go too. Its root folder stays in the catalog, even with nothing left in it, as Lightroom keeps a folder when its last subfolder goes; **Remove from Catalog…** in an empty root folder's menu takes it out (its folder stays on disk). Refused: a root folder, a folder with one located on its own in it, one holding another root folder or the catalog, a link, a special file, another drive or a file with a second name inside it, a read-only drive, a network drive (macOS has no Trash on one, and Linux's and Windows' on an SMB share aren't used), any drive whose files RAWmakase can't tell apart, a drive whose Trash surely can't take it, and a folder an unfinished file operation involves. Delete and Backspace never act on a folder: they ask about the photos selected in the grid, as in Lightroom. A Trash that takes only part of the folder (possible with Windows' Recycle Bin) leaves it under **Unfinished file operations** until everything is back; after a crash that lost where the Trash put the folder, the item offers **Keep as Is** or **Remove from Catalog**; with that known, **Put Back** renames it back from the Trash. As for photos, the catalog lets the photos go only once the Trash has the folder and it is gone from its path; anything that slipped into the folder in the moment between the last check and the Trash goes with it, and the status line names it when the Trash can be read.

**Export** (Export… at the foot of the Library's left panel, ⇧⌘E, or Develop's Export button) exports every selected photo, each with its own edit, using one set of export settings; in Develop it exports the Filmstrip's selection when the open photo is part of it. Photos it can't export because they are offline are listed in the dialog before you start; a JPEG, PNG or TIFF whose pixels Develop can't read, such as a CMYK JPEG, is reported with the reason when its turn comes, as choosing the photos reads no file. With "Ask what to do", files that already exist are asked about once for the whole export. Exports run one at a time while you keep working: the top bar shows "Exporting 24 / 150", cancels the running one, and lists those waiting so they can be removed. When something was not exported, the top bar says so until you dismiss it; click the message for each photo and why. Selecting a folder or collection and pressing ⌘A selects the photos shown, so filters can leave some out. Rename To offers Lightroom's templates: Filename, Filename - Sequence, Custom Name, Custom Name - Sequence, Custom Name (x of y) and Date - Filename, with a Start Number. Sequence numbers follow the order the photos were chosen, so a photo that is not exported keeps its number; a photo without a capture date is named "undated-" rather than dated by its file. Rename To also offers RAWmakase's own templates (Date Time - Model, "2026-04-24 18.43.24 ILCE-7RM6"; Date Time - Filename; Date - Sequence) and Edit…, Lightroom's Filename Template Editor: a name built from Lightroom's tokens (Filename, Filename number suffix, Copy name, Folder Name, Sequence # and Total #, the capture date's parts, Title, Caption, Copyright, Creator, File Dimensions, Exposure, Focal Length, ISO Speed Rating, Make, Model, Lens, Rating, Label and Custom Text) and text, kept as Lightroom keeps it ("{{date_YYYY}}-{{date_MM}}…"). Model is the camera's model as its file writes it ("ILCE-7RM6"), Make the maker as RAWmakase spells it ("Sony"), as Lightroom shows them; they are read from the files in the background when a template needs them, and Export waits for them. A value a photo lacks is left out and said in the export's notes; the whole name is made a valid file name (`/`, `:`, `\`, `*`, `?`, `"`, `<`, `>`, `|` become `-`), so it can't name another folder. Lightroom tokens RAWmakase doesn't fill yet (Original filename, Import #, Keywords, GPS…) are kept in a template and left out with a note. Post-Processing's After Export can show the exported files in Finder (Explorer, or the file manager on Linux), one window for each folder exported to, up to five; the status line says when there were more.

## Stars, picks and color labels

The selected photo has clickable stars, Pick/Reject/Unflag controls and a color-label menu in both Library and Develop. Grid thumbnails use Lightroom-style gray cells, muted label-colored backgrounds, thin dividers, black photo borders and a lighter selection outline. Stars, pick/reject status and a bordered color swatch appear beneath the photo. Right-click a thumbnail for Set Flag, Set Rating and Set Color Label (all five colors and None). The Library label filter includes imported custom text as well as the five standard colors. Changes save immediately to the RAWmakase catalog, work for offline Library photos, and remain independent for virtual copies. Changing metadata never changes the RAW, its sidecars or the Lightroom catalog.

| Key | Action |
|---|---|
| 1–5 | Set that many stars |
| 0 | Clear stars |
| [ / ] | Decrease / increase stars, bounded to 0–5 |
| P / X / U | Pick / reject / unflag |
| Backtick | Toggle pick / unflag |
| 6 / 7 / 8 / 9 | Toggle Red / Yellow / Green / Blue |
| Shift + rating, flag or color key | Apply and advance in the current filtered order |
| Left / Right | Previous / next photo; in Develop, past photos it can't open |
| Z | Toggle Fit / 100% zoom in Develop |

Purple and **No label** are available in the menu. Repeating a color shortcut clears that same label; ratings set an explicit number, with 0 clearing them. Clicking the currently selected star clears the rating. Shortcuts are suppressed while editing text or numbers, during dialogs and during export; modified system shortcuts such as Command+X are not intercepted. `1` now means one star, replacing its previous zoom shortcut.

The importer reads Lightroom `rating`, `pick` (−1 rejected, 0 unflagged, 1 picked), and `colorLabels`. Missing ratings/flags become zero; missing labels become empty. Label text is preserved exactly, including custom/localized names. Standard Lightroom label names map to the corresponding color. Other text displays white and remains searchable/filterable; a custom Lightroom label-set mapping is not reliably available from a standalone `.lrcat`, so RAWmakase does not guess its color. No write-back/synchronization with Lightroom is performed. In the Grid, rating, flag and label keys apply to every selected photo. Each change is one step that Cmd+Z undoes and Cmd+Shift+Z redoes, in the same undo sequence as Develop; it is kept in memory and cleared when another catalog opens. Caps Lock auto-advance is not implemented.

Shortcut reference: [Adobe Lightroom Classic keyboard shortcuts](https://helpx.adobe.com/lightroom-classic/desktop/introduction-to-lightroom-classic/keyboard-shortcuts.html).

## Import and preservation

The importer takes a private snapshot of the source, checks its SQLite structure/integrity, and imports in one transaction. It requires a closed/exported catalog without a nonempty WAL/journal; it refuses an active/incomplete copy rather than ignoring pending changes. The importer has no size limit and was exercised on the supplied Lightroom v13 catalog. Incompatible layouts fail without leaving a destination file.

Normalized tables retain images and virtual-copy identities, original paths, folder roots, capture dates, ratings, flags, color labels, collections/memberships, keywords/parents/memberships, serialized Develop settings and Develop history steps (the `lightroom_history` table, shown under **From Lightroom** in the History panel, where each step can be applied). Imported collection sets and collections can be browsed, read-only, in the Library's Collections panel; smart collections stay hidden until their rules are evaluated. The Quick Collection (B, Cmd+B, Cmd+Shift+B) is the only collection whose photos can be changed. Keywords can be added and removed in the Keywording panel, for every selected photo, as one undoable step. Lightroom's hidden root keyword, a nameless one its top-level keywords are under, is imported as it is but never shown, searched or exported: a typed top-level name is found under it, and a new top-level keyword goes under it, as in Lightroom. A byte-exact copy of the entire source `.lrcat` is stored in `sources.original_catalog`, preserving snapshots, collection stacks, IPTC, GPS, faces, smart rules and other fields that RAWmakase does not yet interpret. This makes the new catalog larger; it avoids discarding unrecognized Lightroom data. A catalog over 900 MB is too large for one SQLite blob (1,000,000,000 bytes in the bundled build), so it is imported with an empty archive: everything the importer copies is kept, but fields it does not interpret are not. External `.lrcat-data`, preview bundles, originals and profiles are not embedded or synthesized.

Smart collection definitions and any stored membership are preserved; RAWmakase does not evaluate Adobe's smart-collection rule language. Collections marked “smart snapshot” may therefore have no stored members.

## Descriptive metadata and XMP sidecars

Title, caption, creators, copyright, capture time, location and keywords are kept per photo in the catalog; a virtual copy has its own once created. A field with no value in the catalog is the file's own (its EXIF, at export); a cleared field leaves the file's out too.

**Lightroom import** reads each photo's title, caption, creators, copyright, capture time and location from the XMP Lightroom keeps in its catalog; keywords, ratings, flags and labels come from Lightroom's own tables. Catalogs imported before this read it once when opened.

**Add photo folder** reads, for each new photo, its XMP sidecar and, for JPEG, TIFF, PNG, WebP, AVIF, HEIF, JPEG XL, DNG and Canon CR3, the XMP inside the file (title, caption, copyright, creator, capture time, location, keywords and rating; the camera comes from the file's EXIF). A CR3's is the XMP the camera writes, so a rating given in the camera comes with the photo, as in Lightroom; the XMP inside other proprietary RAWs (ARW, NEF, RAF and others) is not read. A JPEG XL's metadata boxes are read also when brotli-compressed ("brob"), as cjxl writes them by default. A RAW's sidecar is `IMG_1234.NEF.xmp` (digiKam's default), else `IMG_1234.xmp`; when both exist the first is used and the other is listed as ignored. `IMG_1234.xmp` beside both `IMG_1234.NEF` and `IMG_1234.JPG` is the RAW's; the JPEG reads only `IMG_1234.JPG.xmp` and its own XMP, field by field, the sidecar's winning, and an explicitly empty sidecar value clearing the field. Sidecars that can't be read are counted in the top bar; click the message to list them. Adding a folder again does not read the sidecars of photos already in the catalog. Each new photo is written together with its metadata, its default Creator and Copyright and any edit an earlier release saved beside it, so a failed write (a full disk) leaves none of the folder's new photos, and adding the folder again adds them complete.

**Read Metadata from Files…** (thumbnail menu) does, for the selected masters: every field a file has replaces the catalog's, your edits included; fields the file lacks are kept. It asks first, is one step for Undo, and never reads into virtual copies.

Keywords are read from `lr:hierarchicalSubject` ("|" between levels), else `digiKam:TagsList` ("/"), then any `dc:subject` name no path has, as a top-level keyword; with neither, `dc:subject` is flat keywords. digiKam's color labels map to Lightroom's names (red, yellow, green, blue, purple; others by their color name) and its pick labels to picks and rejects. What can't be reconstructed: a name containing "|" (or "/" through digiKam) read from another tool's file becomes a hierarchy; a top-level keyword named like an element of a hierarchy, in a file without a path for it, merges into that hierarchy; the parents of a keyword with "|" in its name are lost on a round trip.

Not read or written: IPTC location and contact fields, headline, credit, source, usage terms, instructions, people and face regions, other digiKam data, ratings in other namespaces, XMP history and unknown namespaces. Sidecars are never written. A virtual copy created by RAWmakase 0.1.12 or older has no values of its own and uses the file's until edited.

## Lightroom rendering

A photo without a RAWmakase edit opens with its Lightroom edit applied, once camera profiles are known. **Apply compatible Lightroom edits** re-applies it as one undoable change using RAWmakase's supported controls. It parses Lightroom's serialized settings as data, never as executable Lua. Lens corrections, Transform and Upright (from Lightroom's stored corrections) apply. It reports missing profiles and unsupported controls, such as AI and color-range masks, Glow and Reshape. A look's Profile Amount applies to looks that support it ([Profile Amount](lightroom-profiles.md#profile-amount)); an Amount outside 0–200% is reported and renders at 100%. Spot removal, red eye corrections and brush, gradient, radial and luminance-range masks convert to RAWmakase's experimental spots, red eye (and Pet Eye) corrections and masks. Compatible controls use RAWmakase's algorithms; this is not a Lightroom appearance guarantee. The untouched original settings remain in the database even after further editing. Lightroom orientation metadata is preserved; current previews/Develop use the source camera orientation.

## Relinking offline photos

On Linux, Lightroom's `/Volumes/...` and `/Users/...` paths will often be offline. Click the **…** on a root row, or right-click it and choose **Locate root folder…**, to map a complete source root to its local directory. The **Browse…** button opens the native directory picker for the selected tree folder; choosing a directory applies the mapping, and Cancel leaves it unchanged. After relinking, RAWmakase reports the available photo count. Right-click a folder and choose **Locate this folder…** for a narrower mapping; a folder holding only folders (such as a shoot's folder above its `RAW/Card 1` folders) can be located too, and every folder below it follows. Descendants inherit a folder mapping; a more specific mapping takes precedence. In the Folders panel a folder located on another drive shows under that drive, after its root folders, with the folders in it; its root folder still counts its photos and shows them when chosen, as they are still in it. Paths are changed only in the RAWmakase catalog. Files are never moved, renamed or matched by filename alone.

When only some photos moved, or moved somewhere the catalog doesn't know, right-click an offline photo and choose **Find on Disk…** (also in Develop's **Photo** menu for the photo open there; for a virtual copy it finds its master). The file picker starts in the nearest folder of the photo's old place that is still there. Pick its file: RAWmakase checks it against the checksum on record and refuses a file whose size, quick hash or full checksum says it is a different photo. Then it looks in the same folder (not its subfolders) for the other offline photos of the photo's catalog folder. A file whose full checksum matches is ticked; one that matches only by its quick hash, or by the file its edit was saved for, is **probably** that photo, and one with the same name, for a photo without a checksum, is offered **not verified**: both start unticked. The review is titled `Found 8 other missing photos in this folder`, and **Relink 9 Photos** updates their catalog rows, so ratings, flags, keywords, collections, metadata, edits, History, snapshots and virtual copies stay with them. When only the file picked is found, verified, it is relinked straight away and the top bar says `Relinked 1 photo`. A file picked without a checksum to verify it is still taken, as you chose it, but its edit stays protected as after a probable move. A folder no catalog folder covers is added as a new root folder, holding only the photos relinked into it: Add Folder or Synchronize adds its other files later. A folder that holds root folders of the catalog, or that another location of the catalog claims, is refused. If the photo's old drive isn't connected, only a verified match is offered, and the review warns that the catalog uses the file found from now on, even if the old one is still there. The photo open in Develop follows only a verified match, its unsaved edit kept and saved at the new place; for any other file picked, open another photo in Develop first. Find on Disk adds no photos, so Previous Import stays as it was. `rawmakase find-photo CATALOG PHOTO_ID FILE [--apply]` does the same from the command line.

## One catalog on several computers

RAWmakase reads a checksum of every master photo's file in the background, so that a photo moved or renamed outside RAWmakase can be found again: a quick hash of three 64 KiB blocks for every photo first, then the SHA-256 of the whole file, one file at a time and at most 64 MB/s. Reading waits while an export runs, previews are built or Develop opens a photo. A checksum is kept only while the file is unchanged, and is read again when it changes; a virtual copy has none of its own, and Set Copy as Master hands its master's over. **Preferences › Catalog** shows how many photos have one and can pause reading them. Nothing is written beside the photos.

## Synchronizing folders

**Synchronize Folder…** (right-click a folder or root in the Folders panel, or the Catalog menu for the folder selected) and **Synchronize All Folders…** (Catalog menu) bring the catalog back in line with files changed outside RAWmakase. A photo moved or renamed keeps its catalog row, so its rating, flag, label, keywords, collections, metadata, Develop edit, History, snapshots and virtual copies stay with it. Nothing on disk is moved, renamed or deleted.

The scan runs in the background while the Library and Develop stay usable; the top bar shows `Synchronizing "Lisbon" · 1,240 files` with a stop button. Each folder is looked for where it is on this computer, and a photo counts as missing only when its folder was listed and lacks it (or the folder is gone from a location that is there and online); an offline folder or volume is listed under Not checked, never as missing. Files no photo names are matched with the checksums on record: a file whose full checksum equals a missing photo's is that photo, moved; one that matches only by its quick hash, or by the file its edit was saved for, is **probably moved** and left unticked; a byte-for-byte copy of a photo still there is offered unticked under **Add copies…**; several candidates are left for you to pick from.

When the scan finishes, **Review synchronization** opens automatically in Library or Develop once any other dialog has closed. Moved photos and new files start ticked; probably-moved photos, copies and **Remove missing photos** start unticked. Removing photos that hold edits, ratings or copies asks first. Applying checks every action again and skips anything that changed since the scan; the top bar reads `Synchronized · 14 updated · 32 added · 5 still missing`, with the details on hover. A moved photo's edit opens on its new file when the move was verified and the edit was saved for exactly that file; otherwise it stays protected, as it was. The photo open in Develop follows a verified move of its file, its unsaved edit kept and saved there. New photos get their sidecar metadata, legacy edits and default Creator and Copyright as Add Photo Folder gives them, and become **Previous Import** (Catalog section), which holds the photos the last Add Photo Folder or Synchronize added; after a synchronization that added photos, the status bar offers **Show**.

`rawmakase sync-folder CATALOG [FOLDER] [--apply]` prints the same plan from the command line, and applies what the review ticks by default with `--apply`.

Each computer keeps its own location for the catalog's folders, so a catalog taken from a Mac to a Linux machine (and back) finds its photos on both, even when the NAS is mounted at `/Volumes/Photos` on one and `/mnt/nas/photos` on the other. Locating a folder only changes where it is on the computer you're using. **Preferences › Catalog › Folder locations** lists every root with its location on this computer ("as added" when it has none), whether it is found, and the folders below it located separately, each with **Change…** and **Clear**. Clearing a folder makes it follow the nearest location above it; clearing a root makes it use the path it was added with and keeps its folders' own locations. Changing a root or a folder that has such folders below it asks whether to keep them or clear them. Other computers' locations are shown for reference, and **Find Missing Folder** starts where another computer has the folder when that path exists here too. A location that is offline stays offline: RAWmakase never falls back to another path.

Each install has a random computer id, kept in its local data folder (never in the catalog or a synced folder); the computer's name is only a label and can be changed. The first time a computer opens a catalog with this release, it copies the catalog's existing mappings as its own, so nothing moves.

Adding a folder matches every folder found on disk, the one you chose and every one below it, with this computer's locations. A folder another location already covers joins that catalog folder, so adding the same share on a second computer adds no new root and no duplicate photos. A folder whose catalog folder is located elsewhere on this computer (an old copy left behind after locating it somewhere else) is skipped and reported. When two catalog folders match equally, RAWmakase asks which one it is. Folders added on Windows now resolve on macOS and Linux; a Unix folder name containing `\` stays one name, and is unavailable on Windows.

Older releases still open the catalog: they read and write a single mapping for all computers, as before, and the newer release writes that mapping too. Their changes don't move folders on a computer that has already opened the catalog with this release, and a root they add is found where it was added until it is located there. A folder located while the catalog has no folder of its own for it (one holding only folders) isn't seen by them: they find the folders below it through their own locations, else their root's.

Keep only one computer using a catalog at a time: close it on one before opening it on another. SQLite over a network share isn't safe for two computers writing at once.

## SQLite format, versions 1 to 4

New and imported catalogs are version 3. Version 2 can hold raster masks (content-addressed in the `bitmaps` table, referenced by recipes, History and snapshots, never deleted). Version 3 holds edits rendered by the one engine: every stored recipe (edits, History steps, snapshots) has lost the settings earlier releases chose a rendering engine or operator with (`model::saved_format::OBSOLETE_SETTINGS`); slider values and settings this release does not know are kept. Version 4 may hold Lensfun lens choices (an edit, a History state or a snapshot naming a Lensfun lens, with its copy of the calibration; see [lens corrections](lens-corrections.md#lensfun-profiles)), which releases before Lensfun would read as an Adobe profile without a name and save without it. Releases before each version refuse it, the file left unchanged.

A version 1 or 2 catalog opens, browses and takes ratings and metadata as before, and is read with the one engine. It is upgraded the first time a recipe is stored in it (saving an edit, its History or a snapshot, importing a legacy sidecar), or earlier from the Masking drawer's **Upgrade catalog…** for Select Subject or Select Background. The upgrade first writes a verified SQLite copy beside the catalog (`<name>.before-upgrade-backup`, then `-1`, `-2`…, as large as the catalog; it is a recovery copy, not a second catalog, and opens in the release that used the catalog before), then rewrites the stored recipes and changes the version in one immediate transaction: a failure leaves the catalog as it was, with the backup, and the save fails and stays pending. Close the catalog on every other computer first; mixed-version concurrent use is not safe. A catalog is raised to version 4 the same way, with a backup and in the same transaction, by the first write that stores a Lensfun choice, in use or not, resolved or not (saving an edit whose recipe or any History state names one, a snapshot, a legacy sidecar's edit); other writes leave it at 3. Export as Catalog copies the catalog's version, so a catalog holding Lensfun choices exports as version 4.

A `.rawmakase` file is SQLite with application ID `0x4f4d4152` and `PRAGMA user_version` 1 to 4. Core tables: `sources`, `roots`, `folders`, `photos`, `collections`, `collection_photos`, `keywords`, `photo_keywords`, `folder_mappings`. `import_batches` and `photo_imports` record which Add Photo Folder or Synchronize added each photo (Previous Import is the newest batch). `photo_checksums` keeps each master's file checksum (size, quick and full SHA-256, the `Identity` of the version read and the hashing version); it is new without a format change, so older releases ignore it, and its rows go with their photo. Per-computer folder locations live in `computers`, `folder_paths` (each folder's logical path, names joined by `/`) and `folder_locations`; `roots.mapped_path` and `folder_mappings` are kept for older releases. `file_operations` and `file_operation_members` are the journal of file operations (moving and renaming photos' files, renaming and moving folders, putting files in the Trash, with where the Trash put each): each item and each file it touches, written before every step, so an operation a crash cut short is finished, put back or reported by recovery, never guessed; photos moved or renamed within a drive are journalled up to 100 items in one commit, and each step of theirs (every item's photo, then every item's next file) is synced once per folder and journalled in one commit, so each item's files still go one after another, each synced and journalled before its next (#692); recovery runs before every file operation and when the Library opens the catalog. Making a folder is journalled too: its path before it is made, its file object and the name the disk gave it after, so a folder whose making wasn't recorded is never added to the catalog for it. `file_operation_copies` is what a move to another drive copies, a row for each file: its hidden partial copy's path, journalled before it is made, the copy's file object once it is, the SHA-256 it was verified with, its `Identity` once the catalog follows it, where the Trash put the copy when the move was undone, and why an original stayed; such an item is `committed` once the catalog follows its copies and `done` once its originals are dealt with. A folder moved to another drive is one such item: its members are the folder, the folders in it, then its files, each with a row there (its place inside the hidden folder as `temp`), and its journalled state says how many of them are folders. A partial copy is the one file RAWmakase ever deletes outright, by its journalled file object or, made but not yet journalled, at the name the journal gave it and only while empty, and never on an SMB share; a whole copy goes only to the Trash. They (and `file_operation_copies`) are new without a format change, so older releases ignore them (an unfinished item's checks are made again first, so a change an older release made meanwhile is reported, not acted on); finished items are forgotten after 30 days. While files are being changed (not for Remove from Catalog, which changes none), RAWmakase holds an OS lock on `<catalog>.file-operations-lock` beside the catalog (named after its real path, through any link), so a second window can't change the same files; the file is left in place. A rename keeps each file's extension and renames the sidecars only it reads to match, refuses the whole rename when any name is taken, given twice or another photo's in the same rename, and renames a folder, or moves it into another folder of its root on the same drive, only when nothing below it is located on its own, re-keying `folder_paths` and the legacy `folders.relative_path` of its subtree. Remove from Catalog is journalled too. A folder put in the Trash is a `trash_folder` item: its state is the subtree's catalog folders and photos, each family's digests and how its names are proven, and its members are every name of the tree (the folder, its folders, then its files), each `trashed` with where the Trash put it. It is new without a format change, but a release before it (0.4.2 and earlier) can't read the kind and fails closed on an unfinished one rather than act on it: on the computer that made it, its recovery fails and so does every file operation that takes the lock; on any computer, Remove from Catalog and planning a folder rename or move fail with that error; until this release decides the item or the user keeps it. A finished one is never read by those releases. A root folder moved into another root is a `move_root` item (#586), a folder item like `move_folder` whose state moves the root's own logical path (`""`), so a release before it (0.4.6 and earlier) fails closed on an unfinished one the same way rather than take it for a folder move within a root; this release reads `move_root` only with that path and `move_folder` and `rename_folder` only without it. The transaction that re-keys the root's folders into the other root also removes the root and its locations on every computer. Foreign keys are enabled. Photo recipes and export options are JSON fields, separate from `lightroom_develop`. Saved recipes include source identity checks, so a replaced file cannot silently overwrite a previous edit. Unknown future catalog versions are refused.

Creation/import publish atomically without clobbering another file. SQLite transactions protect metadata and recipe writes. Back up the `.rawmakase` file with RAWmakase closed. No Lightroom file or RAW is modified by catalog operations.

## CLI

```sh
rawmakase import-catalog input.lrcat Photos.rawmakase
rawmakase catalog-info Photos.rawmakase

```

`catalog-info` lists source root IDs and their locations on this computer; `relink-catalog` changes a root's location on this computer only. Synthetic tests exercise exact source preservation, archived bytes, virtual-copy isolation, metadata, collections, keywords, descendant relinking, idempotent folder imports, changed-source protection, malformed/active catalog rejection, rollback and no-overwrite behavior.

## Decoded-image cache

Preferences > Catalog > **Decoded images > Cache size limit** sets how much disk space
to keep for decoded RAWs, from 1 GiB to 1 PiB (1,048,576 GiB; 4 GiB by default). This cache is
shared by all catalogs and avoids repeating RAW decoding and highlight recovery
when reopening a photo; the current edit still needs rendering. Develop, neighbour
preloading and Reference View share the limit. Changes are saved between launches
and apply without restarting; lowering the limit removes least recently used
entries on the next cache write. Rendered Standard and 1:1 previews have separate
budgets. See [the decode cache](preview-performance.md) for its location and identity.

## Preview cache

Library thumbnails are generated on demand and stored as JPEG blobs in a separate `~/.local/share/rawmakase/previews.sqlite3` database (`$XDG_DATA_HOME/rawmakase`, or `RAWMAKASE_DATA_DIR` when configured). All catalogs share this disposable cache. A thumbnail from an older preview generation is made again when next shown: JPEG, PNG and TIFF thumbnails made before their ICC profile was honoured are replaced, while RAW thumbnails are kept. Catalog databases continue to hold metadata and edits only, apart from the preserved Lightroom source archive.

The cache checks file size, nanosecond modification time, a prefix fingerprint and the preview generation version before reuse. Previously generated previews remain usable while originals are offline. Missing Lightroom preview bundles cannot be reconstructed from the `.lrcat` alone; a photo needs to be available at least once to generate its preview.

SQLite WAL permits concurrent readers/workers. The image-payload budget is 512 MiB with least-recently-used eviction; an additional 192 thumbnails are retained in GPU memory. Corrupt individual images are discarded and regenerated. Cache failure falls back to uncached previews. With RAWmakase closed, the preview database and its WAL/SHM companions can be deleted without losing edits. This cache currently covers original Library thumbnails, not full-resolution Develop renders.

The same file has room for larger previews built on request (issue #213): Standard previews, sized for Develop to show while a photo opens, and 1:1 previews at full resolution. They are keyed by file, by an identity of the edit they show and by kind, so virtual copies and edits each get their own row, and they follow the thumbnails' offline and staleness rules. Each kind has its own least-recently-used budget (Standard 2 GiB, 1:1 4 GiB), so building one never evicts thumbnails or the other kind. A row records the edge it was built for apart from the size it reached, so a small original or a tight crop is not rebuilt each time. Which catalog photos had previews requested is kept in its own table, per catalog and photo, so a virtual copy or the same file in another catalog never inherits them; discarding a photo's previews or removing it from the catalog forgets the request. These tables were added without changing the cache's format version, so older builds keep opening the file.

**Build Standard-Sized Previews**, in a thumbnail's menu under Previews (in the Library grid and the Develop filmstrip), builds them for the selection, or the photo clicked when it is not selected. Offline photos and files Develop can't open are skipped and counted, and photos whose preview is still fresh cost nothing. Each photo is rendered as an export would render it, from its edit as the catalog has it then (the open photo's is saved first): a protected or unreadable edit fails that photo with its reason and never falls back to the defaults, and Upright is worked out first. The half-size decode is used when it is large enough once cropped and transformed, else the full one. Builds run one at a time in the background, never blocking navigation; the top bar shows "Building previews 12 / 150" with a button that stops them, then what could not be built. A photo shown edited in the grid takes the build as its thumbnail too, unless Develop rendered it, or its edit changed, since. **Discard Standard and 1:1 Previews** removes the files' built previews and the photos' requests. Preferences > Catalog sets the **Standard Preview Size** (1440, 2048 or 2560 pixels, 2048 by default), shows what thumbnails and each kind of preview take, and clears Standard previews. Automation's `build_previews` does what the menu does for the selection.

While a photo opens in Develop or the Loupe, its Standard preview for its current edit, when there is one, is shown at once, in place of the camera's embedded JPEG, until the first live render replaces it; the next photo's is read ahead. It is only a picture: the readout, white balance picking, the histogram, tools and Before/After wait for the photo itself. An offline RAW, or an edited JPEG, PNG or TIFF, in the Loupe shows its Standard preview instead of the grid's thumbnail. **Build Standard-Sized Previews** skips a JPEG, PNG or TIFF without an edit: its file is its preview. When a photo whose previews were built is saved with another edit (on leaving it, by Sync or Paste Settings, or an Undo of those), its Standard preview is built again; a virtual copy, or the same file in another catalog, has its own requests and is not rebuilt with it. Measurements are in [preview performance](preview-performance.md#stored-standard-previews--2026-10-08).

**Build 1:1 Previews**, in the same menu and through `build_previews` with `kind: one_to_one`, keeps each photo at full size, rendered from the full decode. Their one use is an offline RAW in the Loupe: a click zooms it to 100% from its 1:1 preview, where without one zooming needs the original. Online photos zoom from the photo itself, which once decoded presents a 100% region in well under 0.1 s, so a 1:1 preview would not make that faster ([measurements](preview-performance.md#11-previews--2026-10-08)). A 1:1 preview is large (a 61 MP photo's is tens of megabytes), so they are kept in the cache with their own 4 GiB budget, and Preferences > Catalog discards those unused for a day, a week or 30 days (the default), or never, as Lightroom's Automatically Discard 1:1 Previews does; **Discard 1:1 Previews** and **Clear 1:1 Previews** remove them at once. A photo larger than a JPEG can hold (65,535 pixels a side) is reported and not kept.

The folder tree uses expandable nested rows and aligned counts. Selecting a folder includes its descendant folders. Shift-click selects the folders shown between the folder last clicked and this one, and ⌘-click (Ctrl-click on Windows and Linux) adds or removes one, so the grid shows several folders' photos together; the last folder can't be removed this way. The source name reads "3 folders", Synchronize Folder in the Catalog menu needs a single folder (right-click a folder to synchronize it), and on the next launch the Library returns to the folder the selection started from. Library and Develop are available through the workspace tabs or G/D shortcuts.

On Linux, desktop network shares require the GVFS FUSE bridge for native filesystem access. RAWmakase starts the installed `gvfsd-fuse` helper when needed before catalog loading or directory selection. Existing GVFS mounts and desktop-managed authentication are reused; no credentials are stored by RAWmakase.
