# Native dependencies

RAWmakase links no native imaging library. RAW files are decoded by its own decoders, in Rust (`crates/rawmakase-raw`, see [RAW decoding](raw-decoding.md)), and colour is managed in Rust (moxcms reads the ICC profiles). Earlier releases linked LibRaw and Little CMS; neither is built, linked or shipped any more, and `scripts/crate-closures.sh` fails if a crate or build script brings one back. The only C compiled into the app comes with Rust crates' own sources (the catalog's bundled SQLite in `libsqlite3-sys`, ring, Wayland's backend on Linux); ring needs clang on Windows ARM64 (`packaging/windows/toolchain.ps1`). The project's MIT license applies to RAWmakase's original code; Rust dependencies retain their own licenses. Do not bundle native libraries without their notices and applicable distribution requirements.

Release DMGs, DEB/RPM packages, the Linux archive and AppImage bundle no private library except ONNX Runtime (below); Linux packages rely on the system's C++ runtime (for ONNX Runtime) and graphics libraries, and Windows links the C runtime statically. See [release packaging](../packaging/RELEASING.md).

Subject and Background selection runs two ONNX models, and Sky a third, through ONNX Runtime 1.23.2 (MIT; the packages' `licenses` carry its LICENSE and ThirdPartyNotices), opened lazily by `rawmakase-inference` from beside the executable. The runtime is bundled per package by `packaging/onnxruntime.py` (pinned archive and SHA-256 per platform, 1.23.2 being the last release with an official macOS x86_64 build). The Arch recipes download the same archives through makepkg, with the same SHA-256s (`packaging/test_onnxruntime.py` checks they agree), and install the library in `/usr/lib/rawmakase/`; they do not use Arch's `onnxruntime-cpu`, a newer release RAWmakase is not tested with. The models are not bundled; the app downloads them on request from RAWmakase's mirror, [`pch/rawmakase-models`](https://huggingface.co/pch/rawmakase-models) on Hugging Face, pinned to a commit, falling back to the repositories the mirror copied them from, also pinned. Each file is verified by SHA-256 before use (`rawmakase-inference/src/manifest.rs`). The mirror holds SAM 2's and DETR's files unmodified and RAWmakase's own UperNet export, with the licence texts, a NOTICE giving each file's source repository and commit, and a model card; update all three, and the manifest's commit, when a model changes:

- **Segment Anything 2.1 Hiera small** (Meta AI): four files of the Hugging Face `onnx-community/sam2.1-hiera-small-ONNX` export at a pinned commit. Meta releases the code and checkpoints under Apache-2.0 (the `facebook/sam2.1-hiera-small` card says `apache-2.0`); the export repository declares no license of its own.
- **UperNet ConvNeXt base** (OpenMMLab, trained on ADE20K), for Sky alone: RAWmakase's own half-precision ONNX export of `openmmlab/upernet-convnext-base` at a pinned commit, written by `scripts/models/export_upernet_sky.py`, which reproduces it byte for byte. No upstream ONNX exists, so the mirror is its only source. The card says `mit` and the code it comes from is MIT (ConvNeXt) and Apache-2.0 (MMSegmentation). The ADE20K images are offered by MIT for "non-commercial research and educational purposes"; the owner reviewed that and accepted it for this checkpoint on 2026-10-30.
- **DETR ResNet-50 panoptic** (Facebook AI Research, trained on COCO): the half-precision ONNX of `Xenova/detr-resnet-50-panoptic` at a pinned commit. The base `facebook/detr-resnet-50-panoptic` card says `apache-2.0`; Xenova's card declares none.

IS-Net, U²-Net and BiRefNet were evaluated and not used: IS-Net's weights have no published license (the author's README licenses only "code and evaluation metric", and the DIS5K training data is non-commercial; the request for a commercial license, xuebinqin/DIS issue 150, is unanswered), and the BiRefNet weights are MIT but were trained on DIS5K as well (a training-data question of the kind since accepted for ADE20K, so that alone no longer rules BiRefNet out; IS-Net's unlicensed weights still do). Before adding or replacing a model, record its weights license (not its code's) and its training data's terms here.

Lensfun's lens database (#662; [lens corrections](lens-corrections.md#lensfun-profiles)) is not bundled and RAWmakase links none of Lensfun's code: the database is CC BY-SA 3.0 (Lensfun contributors), the library LGPL-3.0 and its tools GPL-3.0. The app downloads the database only when the user asks (Lens Corrections' card, Preferences › Profiles & Presets, `rawmakase lensfun install`), from Lensfun's own update channel (`https://lensfun.github.io/db/versions.json` and `version_2.tar.bz2`, what `lensfun-update-data` uses), unmodified, into the data folder; every offer to download names the source, the attribution and the license with a link to it, and `licenses/Lensfun-database-CC-BY-SA-3.0.txt` (the license text Lensfun ships with the database, copied verbatim; the archive itself holds none) is in every package. RAWmakase reads the XML format and evaluates its models with its own code, written from Lensfun's documentation and checked against the output of Lensfun built offline at revision bc5615d6 on synthetic calibrations (`crates/rawmakase-model/tests/data/lensfun`: the calibrations are made up, `probe.cpp` is RAWmakase's own program against Lensfun's public API; no Lensfun source is copied or translated, and no Lensfun data is committed). An edit that uses a Lensfun lens keeps a copy of that lens's calibration in the catalog (or a preset or legacy sidecar): treated as Lensfun's data adapted, it carries its source, the database's version, the attribution, "CC BY-SA 3.0" and the license's URI, and stays under that license wherever it goes (Export as Catalog included); XMP carries only the lens's identity. Database rights: CC BY-SA 3.0 Unported does not address the EU's sui generis database right explicitly; RAWmakase relies on Lensfun's stated intent that the database be freely used and redistributed (it is redistributed by darktable, RawTherapee, digiKam and Linux distributions), an accepted risk rather than a blocker. The archive is read in pure Rust: `bzip2-rs` 0.1 (MIT/Apache-2.0, a decoder only, not the `bzip2` crate's libbz2 binding) and `tar` 0.4 (MIT/Apache-2.0, without its extended-attribute feature; it brings `filetime`, MIT/Apache-2.0); nothing is unpacked by them to disk, every file being checked in memory first.

Reading WebP, AVIF and JPEG XL uses only Rust crates, so no codec library or `nasm` joins the build or the packages: `image-webp` (through `image`'s `webp` feature, MIT/Apache-2.0), `jxl-oxide` (MIT/Apache-2.0), `rav1d` 1.1.0 (BSD-2-Clause, dav1d ported to Rust) and `yuv` (BSD-3-Clause/Apache-2.0, YUV to RGB conversion). `rav1d` is built with `default-features = false` and only `bitdepth_8` and `bitdepth_16`, so none of its assembly is compiled; its `cc` and `nasm-rs` build dependencies stay unused, and `scripts/crate-closures.sh` fails if anything turns its `asm` features on or brings them in another way. `libc` supplies the errno values rav1d's C interface returns. These decoders only read files; exporting to these formats is not available yet.

Reading HEIF (HEIC) uses `rust_h265` 0.2 (MIT/Apache-2.0, no dependencies of its own, no `unsafe` and no build script) for HEVC, and RAWmakase's own `isobmff` reader and `yuv` for the container and colour; libheif and libde265 (LGPL, C) were not used, as no native imaging library is linked. The same decoder runs on every platform: the operating systems' own (macOS's ImageIO, Windows Imaging Component, which needs Microsoft's Store extensions) were tried and set aside, so that every platform decodes, and is tested, alike; that code is in the branch's history (commit 6d36f2ba). `rust_h265` is the `software-hevc` feature of `rawmakase-decode`, which the app's own feature of that name turns on by default: a build with `--no-default-features` (`make CARGO_FLAGS=--no-default-features`) has no HEVC decoder, and lists HEIF photos, with their size and metadata from the header, but refuses to show or edit them ("RAWmakase can't edit HEIF images"). `rust_h265` is young (first released April 2026), so a panic inside it is caught (`raster/hevc/decoder.rs`) and the file reports an error (the crash log still records it). When it was added, a one-off run over about 31,000 bit-flipped and truncated copies of the HEIC fixtures, not part of the test suite, met no panic or hang. HEVC is covered by patent pools (Access Advance, Via LA) whatever the decoder's license: the code's MIT/Apache-2.0 license grants no patent rights for HEVC itself, and some distributions leave software HEVC decoders out for that reason.

Rust dependencies are resolved in Cargo.lock. The UI uses eframe, pinned to the exact version in `Cargo.toml` (0.36.2 at the time of writing) because egui releases change behavior between patch versions; wgpu provides the GPU compute path. RAWmakase's own colour management (exports' sRGB profile, monitor profiles) is pure Rust, with moxcms reading the profiles; its results were measured against Little CMS 2.19's, recorded in `crates/rawmakase-decode/tests/data/monitor`.

`src/camera_profiles/dng_tone.rs` contains the default ACR3 tone table from Adobe DNG SDK 1.7.1 `dng_render.cpp`, Copyright 2006–2023 Adobe Systems Incorporated, and `src/camera_profiles/temperature.rs` adapts the temperature table from `dng_temperature.cpp`, Copyright 2006–2019 Adobe Systems Incorporated. Their license is included in `licenses/Adobe-DNG-SDK.txt` and in the app bundles and packages. No Adobe camera or lens profiles are bundled; the user imports their own.

eframe's `default_fonts` feature compiles egui's bundled fallback fonts into the binary through the `epaint_default_fonts` crate, pinned at 0.36.2 by the eframe pin. Its four fonts are redistributed here, so their licenses are shipped alongside ours: Hack (`licenses/Hack-MIT-BitstreamVera.txt`, MIT with the Bitstream Vera and public domain DejaVu notices), Noto Emoji (`licenses/NotoEmoji-OFL.txt`), Ubuntu Light (`licenses/Ubuntu-UFL.txt`) and the emoji icon font (`licenses/emoji-icon-font-MIT.txt`). The four texts are copied verbatim from that crate's `fonts/` directory.

The model crate's `storage::fsops` reaches the file system calls moving a user's files needs without hand-written FFI: `rustix` 1.x (MIT/Apache-2.0, already in the build through `tempfile`) on Unix, with its `fs` feature, for `renameat2(RENAME_NOREPLACE)` on Linux, `renameatx_np(RENAME_EXCL)` on macOS and `statfs`/`statvfs` (a volume's facts and, as `f_bavail * f_frsize`, its free space), with `libc` (MIT/Apache-2.0) for the one call rustix doesn't reach, macOS `pathconf(_PC_CASE_SENSITIVE)` (whether APFS tells case apart); and `windows-sys` (MIT/Apache-2.0, which the app already uses) on Windows for `MoveFileExW` without replacing, file ids, volume facts and free space (`GetDiskFreeSpaceExW`, in the `Win32_Storage_FileSystem` feature already used). A copy's steps (`fsops::copy`) use only the standard library and `sha2`. Both are target-scoped dependencies of `rawmakase-model`, and neither brings native code.

The system Trash (`src/platform/trash/`) uses crates already in the build, as target-scoped dependencies of the app: `objc2-foundation` 0.3 (MIT, already there through `objc2-app-kit`) on macOS for `NSFileManager`'s `trashItemAtURL:resultingItemURL:error:`; `windows` and `windows-core` 0.62 (MIT/Apache-2.0, already there through wgpu's backends) on Windows for `IFileOperation` and the progress sink it calls, COM interfaces `windows-sys` has no vtables for; and `rustix` 1.x on other Unix systems, with its `process` feature, for the user id the freedesktop Trash's folders are named after (the rename itself is `storage::fsops`'s). The `trash` crate was not used: its fallbacks are not fail-closed by contract (nothing it promises says a file it can't put in a Trash stays where it was, untouched and never copied across devices), and file operations need exactly that: a receipt naming where the file went, or the file where it was.

The macOS title bar (`src/platform/titlebar.rs`) uses `block2` 0.6 (MIT, already there through `objc2-app-kit`) for the AppKit event monitor's handler.

On Wayland, winit's `wayland-csd-adwaita` feature draws the window's title bar where the compositor leaves decorations to the app, as GNOME does (#754); without it winit drew a bare grey strip with no title. It adds `sctk-adwaita` 0.10 (MIT) with `ab_glyph` and `ab_glyph_rasterizer` (Apache-2.0) and `owned_ttf_parser` and `ttf-parser` (MIT/Apache-2.0) for the title's text. winit makes the frame only when the compositor configures client-side decorations; compositors that decorate windows themselves, or deliberately don't (KDE, Hyprland, Sway), get none. To match the desktop, `sctk-adwaita` runs `dbus-send` (the settings portal's colour scheme and button layout), `gsettings` and `fc-match` (the title font) when it makes a frame; without them it falls back to its defaults. Its failures are logged under its own target, which `app::run`'s eframe error logger ignores.
